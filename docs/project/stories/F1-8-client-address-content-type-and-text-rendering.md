# F1-8: Invented client addresses, simultaneous requests, a wrong content type and markup in user text are not trusted
Status: READY
Security review: touches authentication (security-bot review required)
As a user of the feedback board, I want the server to ignore a client address that a caller invents, to count simultaneous requests correctly, to refuse a request body that is not JSON, and to show any text I type as plain text, so that nobody can get more than the allowed number of requests, send a request from a third-party page without a preflight, or run code in another person's browser through a name or a post.

Traces to the security-bot review of PR #5 (low findings, comment 6458450359 and the re-review of 369411635), the qa-bot suggestions on PR #5 and ADR-002, ADR-004 (PR #2). The invented X-Forwarded-For and the display-name criterion were added in TASK-040 Attempt 4 as F1-7 criteria 5 and 6; in Attempt 5 they moved here (F1-7 was full), together with the new criteria 2, 3 and 5.

## Acceptance criteria
1. Given the per-IP login limit is set to a small N with a long window (technique of F1-2), When I send N+1 login requests through the web server from one client, each with a different "X-Forwarded-For" header value that I invent, Then request N+1 is the first 429 (the invented values do not give a new rate-limit bucket, because the web server overwrites the header with the real client address and the backend trusts it only from the proxy addresses in TRUSTED_PROXY_IPS); and the same holds when the requests reach the backend directly from a peer that is not a trusted proxy (the header is ignored).
2. Given the per-IP login limit is set to 10 with a long window (RATE_LIMIT_LOGIN_PER_IP=10/3600, technique of F1-2), When 20 login requests from one client address arrive at the same time (all sent before any answer is read, spread over two backend worker processes; some with a wrong password, some with an invalid body), Then exactly 10 of them are let through to the normal login logic (answered 401 "INVALID_CREDENTIALS" or 400 "VALIDATION_ERROR", never 429) and exactly 10 are answered 429 with code "RATE_LIMITED" and a Retry-After header of at least 1, and none is answered 500 (ADR-002 limiter tests: 20 simultaneous requests let exactly 10 pass; an invalid body and a wrong password count).
3. Given a sign-up or a login request whose body would otherwise be valid, When it is sent with a Content-Type that the rule refuses (only the media type counts: the part before the first ";", trimmed, compared case-insensitively with "application/json", parameters ignored; test data: "text/plain", "application/x-www-form-urlencoded", "multipart/form-data", no Content-Type, "application/jsonp", "application/jsonx", "text/json", "application/vnd.api+json", "application/json-patch+json", "text/plain; x=application/json", an empty Content-Type value, two Content-Type lines ("application/json" twice, and "application/json" with "text/plain" in both orders) and comma-joined values ("application/json, text/plain", "text/plain, application/json", "application/json,application/json")), Then the response is 415 with the standard error body (code "VALIDATION_ERROR"), no account is created and no session, access token or cookie is issued; and when the same request is sent as "application/json", "application/json; charset=utf-8", "Application/JSON" or "APPLICATION/JSON; Charset=UTF-8" it is processed normally (only the media type is compared, case-insensitively, parameters ignored); and when the 10 requests of that IP and endpoint are already used up in the window, the answer is 429, not 415 (the limiter runs first and every request counts: accepted risk R10, ADR-004 section 7; contract conventions and ADR-004 section 3). The same 415 applies to every endpoint that takes a JSON body (the contract does not list it per operation; invite preview and accept are F3-4 criterion 3; organization create, post create, comment create and status change are F1-9).
4. Given I sign up with the display name "<img src=x onerror=alert(1)>" (a valid length), When my name is shown (in the page header or user menu, as author of a post and of a comment, and anywhere else a name appears), Then the page shows the characters exactly as typed, no HTML element is created from them and no script runs (in the e2e run no dialog event fires and the page has no "img" element with src "x"), and the API returns the name unchanged as a JSON string apart from trimming of leading and trailing spaces (ADR-004: user text is rendered as text only).
5. Given I create the organization "<img src=x onerror=alert(1)>" (28 characters, within the limit of 60), a post whose title and description are that text (within 120 and 2000 characters) and a comment whose body is that text (within 1000), When the organization name (page header, invite preview page, board), the post title and description (board and post detail) and the comment text are shown, Then the page shows the characters exactly as typed, no HTML element is created from them and no script runs (in the e2e run no dialog event fires and the page has no "img" element with src "x"), and the API returns each value unchanged as a JSON string apart from the trimming of leading and trailing spaces that the contract states for "name", "title", "description" and "body" (ADR-004: user text is rendered as text only).
6. Given a sign-up or a login request (the same cases run on invite preview and accept in F3-4 #3), When the body is empty or not valid UTF-8, or the Content-Type value is not valid UTF-8, Then: a zero-byte body (or "Content-Length: 0") with no Content-Type, or with an empty "Content-Type:" value, is answered 415, not 400; a zero-byte body with "Content-Type: application/json" is answered 400 with code "VALIDATION_ERROR", not 415; a body with invalid UTF-8 bytes (for example {"email": " followed by the byte 0xFF) sent as "application/json" and as "application/json; charset=iso-8859-1" is answered 400, never 500 and never a stack trace; a valid UTF-8 body sent with "application/json; charset=iso-8859-1" is decoded as UTF-8 and reaches the body checks; a body that starts with a UTF-8 byte order mark (bytes EF BB BF) before otherwise valid JSON is answered 400, never 500 (ASSUMED and an open question for architect-bot to put into ADR-004 section 3 (not named there today): qa-bot's PR #14 suggestion 4; implementation risk, see Assumptions); a Content-Type value that is not valid UTF-8 ("application/json; x=" followed by 0xFF, "text/plain; x=caf" followed by 0xE9, "application/json" followed by 0xFF) is answered 415, while "application/json; x=café" sent as UTF-8 bytes is accepted and reaches the body checks; and in every refused case no account is created and no session, access token or cookie is issued (ADR-004 section 3 (PR #14, Attempt 10 tests; ADR-004 labels them ASSUMED, not approved by Gopi) and the contract's Content-Type convention).

## Business rules
- The client address for rate limiting comes from the right-most entry of X-Forwarded-For, set by exactly one trusted proxy (nginx); other peers' X-Forwarded-For is ignored; IPv6 addresses are grouped by /64 (contract, ADR-002; accepted risk R15).
- A request counts toward the per-IP limit when it reaches the limiter, whether or not it succeeds and whatever its body or Content-Type; under simultaneous requests the count must not be lost (shared counter store, ADR-002).
- A request with a body must send a Content-Type whose media type is "application/json" (only the media type is compared: the part before the first ";", trimmed, case-insensitive, parameters ignored; exactly one non-empty header line), otherwise 415 with the standard error body and no change; the 415 check comes after any IP-keyed limiter (sign-up and login have one) and before authentication (contract conventions, ADR-004 section 3).
- Content-Type comparison (source: ADR-004 section 3 and the contract on main, merged with PR #7; ADR-004 itself marks the comparison details ASSUMED, so they stay ASSUMED here): only the media type is compared, that is the part before the first ";", trimmed, case-insensitively; parameters are ignored. "application/json", "application/json; charset=utf-8", "Application/JSON" and "APPLICATION/JSON; Charset=UTF-8" are accepted. Everything else gets 415: "text/plain", "application/x-www-form-urlencoded", "multipart/form-data", no Content-Type, "application/jsonp", "application/jsonx", "text/json", any "+json" type such as "application/vnd.api+json" or "application/json-patch+json", and "text/plain; x=application/json" (a parameter never changes the media type); also an ambiguous header: an empty value, more than one Content-Type line (even two identical lines) or a comma-joined value such as "application/json, text/plain" (ADR-004 section 3, ASSUMED there).
- Empty body and UTF-8 decoding (source: ADR-004 section 3 (PR #14, Attempt 10 tests; ADR-004 labels them ASSUMED, not approved by Gopi) and the contract's Content-Type convention, all ASSUMED there): the Content-Type is judged before the body is looked at; on a body-carrying endpoint a missing or empty Content-Type is 415 even when the body is empty, and "application/json" with an empty body is 400 "VALIDATION_ERROR"; the Content-Type value is decoded as strict UTF-8 (invalid bytes give 415, no Latin-1 fallback); the body is decoded as UTF-8 whatever the charset parameter says, and a body that is not valid UTF-8 gives 400, never 500. "/auth/refresh" and "/auth/logout" take no body, never read the Content-Type and never answer 415.
- All user-supplied text is rendered as text only: no dangerouslySetInnerHTML, no Markdown or HTML rendering, no automatic links (ADR-004).

## UI notes
- None. A request rejected with 415 or 429 is shown like any other error (ASSUMED, as in F1-2). Sign-up and login need no CSRF header and no bearer access token (both are public in the contract): the page sends exactly one "Content-Type: application/json" on them, and "X-Requested-With: feedback-board" is required only by POST /auth/refresh and POST /auth/logout (contract: the CsrfGuard parameter is used by those two operations only; ADR-004 section 3; F1-3).

## Data touched
- None written by criteria 1 to 3 and 6 (a 415 or a 400 creates nothing; criterion 2 creates no session because no password is correct); criteria 4 and 5 store the display name, organization name, post and comment text as typed (trimmed).

## Out of scope
Rate-limit thresholds and the 429 format (F1-2), forged tokens and a deleted membership (F1-7), the 400 and 415 cases of invite preview and accept and their order of checks (F3-4), the 415 on organization create, post create, comment create and status change (F1-9), the IPv6 /64 grouping test (no criterion; ADR-002 lists it for qa-bot, see the TASK-040 handoff), the display-name length rule (F1-1), a content security policy test for script injection beyond the page header check (F1-4 criterion 6), IP spoofing through a second proxy in front of nginx (accepted risk R15: exactly one proxy is assumed).
