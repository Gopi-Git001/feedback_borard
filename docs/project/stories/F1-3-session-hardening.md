# F1-3: Harden the session: refresh-token reuse, request guard and bearer-token rule
Status: READY
Security review: touches authentication (security-bot review required)
As a user, I want a stolen or replayed refresh token and a forged cross-site request to be stopped, so that nobody else can keep or take over my session.

Traces to brief feature F1 and to the human-approved additions in brief.md (refresh tokens stored server-side with rotation and a 7-day absolute cap). The behaviour is specified in the API contract, ADR-002 and ADR-004 (PR #2); the criteria below turn it into testable steps. Normal refresh, logout and the per-IP rate limits are in F1-2; concurrency (logout versus refresh) is in F1-5; cookie flags and headers are in F1-4.

## Acceptance criteria
1. Given I logged in and refreshed once, so that my refresh token T1 was rotated into T2 more than 10 seconds ago, When T1 is presented again for a new access token (for example by someone who copied it), Then the response is 401, the whole token family of that login is revoked, the cookie is cleared, and when T2 is then presented, Then it also returns 401 and I must log in again.
2. Given my refresh token T1 was rotated into T2 less than 10 seconds ago (REFRESH_REUSE_LEEWAY_SECONDS, default 10, as in the contract; two browser tabs racing), When T1 is presented again, Then the response is 401 with no Set-Cookie header at all (the cookie that the winning tab just received must survive), no access token is issued, nothing is changed (the family is not revoked), and T2 still works for a new access token (the one case in which a refresh 401 does not clear the cookie; see Business rules).
3. Given I am logged in with a valid refresh cookie, When a refresh or a logout request arrives without the header "X-Requested-With: feedback-board", or with any other value in that header, Then the response is 403 with code "FORBIDDEN", no access token is issued, the cookie is not changed, the token family is not revoked, and a later request with the correct header succeeds; and these two endpoints take no JSON body and never answer 415: with one fresh login per request (no token is reused, and, because the test needs 12 logins and 12 requests (6 refresh, 6 logout), the rate limits are switched off with RATE_LIMIT_ENABLED=false or RATE_LIMIT_LOGIN_PER_IP and RATE_LIMIT_REFRESH_PER_IP are set well above 12 per window, not to the small values of the F1-2 429 tests, so that none of these requests is limited), a refresh with the correct header and no Content-Type, with "Content-Type: text/plain" or with an empty "Content-Type:" value is answered 200 with a new access token, a logout in the same three forms is answered 204, and the same six requests without the correct header are answered 403; any 415, 401 or 429 on these requests is a failure (contract api-contract.yaml:59 and ADR-004 section 3 :32, on main d2e2fdcb4a90250bac374d586379d595e677610a; ASSUMED in ADR-004; test at TASK-010).
4. Given I am logged in with a valid refresh cookie, When a refresh or a logout request carries the correct header but an Origin header that is not the configured frontend origin (for example "https://evil.example", the literal text "null" as sent by sandboxed iframes, or an origin that differs only in scheme, port or a trailing character such as "http://" instead of "https://" or another port), Then the response is 403 with code "FORBIDDEN" and nothing changes (the family is not revoked and the cookie is unchanged; the Origin must match byte for byte, and Origin: null gets 403: contract, ADR-002, ADR-004); a refresh request that the guard rejects is still counted by the per-IP refresh limit, because the limiter runs before the guard (accepted risk R10), while a logout request is never rate limited; and when the Origin equals the configured frontend origin, or no Origin header is sent, with the correct header, Then refresh returns 200 and logout returns 204.
5. Given I hold a refresh token value (the HttpOnly cookie's JWT), When I send it as "Authorization: Bearer" to a protected endpoint such as "who am I", Then the response is 401 (ASSUMED status; the contract says only that a refresh token is never accepted as a bearer token) and no data is returned.
6. Given my session was ended by a logout, or it was evicted because I logged in from an 11th browser (F1-5 criterion 3), When the old refresh cookie is sent to refresh with the correct header, even within 10 seconds of the logout or the eviction (for example log in, log out, then refresh within 1 second), Then the response is 401 with code "UNAUTHENTICATED", no access token is issued, nothing is changed, and the response does send the cleared cookie ("Set-Cookie: refresh_token=; Max-Age=0"): a token revoked by logout, eviction or reuse detection is never inside the 10-second leeway, which covers only a token revoked as "rotated" (contract and ADR-002).

## Business rules
- A token family is the chain of refresh tokens that starts at one login. Reuse of a rotated or revoked token revokes the whole family and answers 401; within 10 seconds after a rotation it answers 401 without revoking (contract, ADR-002, data-model.md).
- **Refresh 401 cookie rule (one rule, the same in the contract, ADR-002, ADR-004 and data-model.md 3.8):** a 401 from /auth/refresh sends no Set-Cookie in exactly one case: the presented token's own row was revoked as "rotated" less than REFRESH_REUSE_LEEWAY_SECONDS (10) seconds ago, and nothing is changed (criterion 2). Every other 401 clears the cookie ("Set-Cookie: refresh_token=; Max-Age=0"): the cookie is missing, or its JWT is invalid, has the wrong type or is expired (F1-2 criterion 2, F1-7 criteria 4 and 5); there is no row, or the 7-day cap has passed (F1-2 criterion 3); the token was rotated 10 seconds or more ago, which is reuse and revokes the family (criterion 1); or the token was revoked by logout, eviction or reuse detection, even a moment ago (criterion 6, F1-2 criterion 4). A 429 never clears the cookie. Documented edge case, no criterion (ADR-002 tests): a token rotated 3 seconds ago whose family was then logged out gets 401 without Set-Cookie.
- The cookie endpoints (refresh and logout) need the header "X-Requested-With: feedback-board" and, when an Origin header is present, it must equal the configured frontend origin; otherwise 403 "FORBIDDEN" with no state change (contract, ADR-002, ADR-004). The Origin must match byte for byte; "Origin: null" is present and unequal, so it gets 403 (contract, ADR-004). This is in addition to the cookie being SameSite=Strict.
- Order for refresh: the per-IP rate limiter runs first, then the guard header and Origin checks (403), then the cookie checks (contract: "the limit is checked before the guard"; ADR-002: the limiter is the first step). A refresh request with a bad Origin or without the guard header is therefore counted by the limiter and can be answered 429 instead of 403 once the limit is used up; a request from a third-party page can use up the quota of the victim's IP address. Decided: limiter first, accepted risk R10 (Orchestrator decision; Gopi Thungam accepted it as R10, ADR-004 section 7). The scope of R10 (which endpoints it covers) is in ADR-004 section 7. Logout is never rate limited, so the refresh limit applies to refresh only.
- Only an access token is accepted as a bearer token; the refresh token is accepted only from the cookie on refresh and logout (contract, ADR-002).

## UI notes
- None beyond F1-2: a failed or rejected request shows the login form again (ASSUMED); the 429 message for sign-up, login and refresh is in F1-2.

## Data touched
- Refresh token records (server side, hash only): revoked state and reason (rotated, logout, evicted, reuse detected).

## Out of scope
Password change or reset revoking all sessions (no such flow in the MVP, ADR-002), CAPTCHA, account lockout or any per-account login limit (out of scope, not offered, Orchestrator decision in TASK-040 Attempt 2; the per-IP login limit is in F1-2; accepted risks R1 and R17 in ADR-004 section 7: distributed password guessing against one account is not limited, with a password minimum of 8 and no breached-password check), the 10-active-families cap (F1-5, ASSUMED in ADR-002), access-token revocation (an issued access token works up to 15 min 30 s, accepted risk R2 and R13; a stolen refresh token replayed inside the 10-second leeway is not detected as reuse, R13; script on the site can call refresh, R9), CORS rules.
