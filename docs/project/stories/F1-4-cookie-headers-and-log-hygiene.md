# F1-4: Session cookie flags, security headers on every response, and clean logs
Status: READY
Security review: touches authentication (security-bot review required)
As a user, I want my session cookie and every response of the app to carry the protective settings, and I want my password and tokens kept out of the logs, so that scripts, caches, other sites and log readers cannot get at my session.

Traces to brief feature F1 and the human-approved additions in brief.md (refresh tokens in an HttpOnly cookie). The values are in the API contract (RefreshCookie, CookieCleared, NoStore), ADR-002 and ADR-004 (PR #2). Added in TASK-040 Attempt 3 after the security-bot review (should-fix 1, 6 and 7). Normal refresh and logout are in F1-2; the request guard is in F1-3; the invite token in logs is in F3-2.

## Acceptance criteria
1. Given I sign up, log in or refresh, When the response arrives, Then its Set-Cookie header sets "refresh_token" with HttpOnly, SameSite=Strict, Path=/api/v1/auth, no Domain attribute (the contract lists none, so the cookie is host-only; ASSUMED reading), and a Max-Age equal to the seconds left until my login time plus 7 days (exactly that value to within 2 seconds: close to 604800 right after login, and smaller by the elapsed seconds after a later refresh, never more than 604800), the JSON body contains an access token but no refresh token, and in the e2e run the browser cookie jar (Playwright context.cookies()) shows the same flags while document.cookie does not list the cookie; Secure is also set, except when the environment sets COOKIE_SECURE=false with APP_ENV "development" or "test" (contract, ADR-002).
2. Given I am logged in, When I log out, or a refresh is answered with 401 for any reason except one (the cookie is missing, invalid, expired, past the 7-day cap, revoked by logout or eviction, or a reused token; the one exception is a token rotated less than 10 seconds ago, which sends no Set-Cookie at all, F1-3 criterion 2), Then the Set-Cookie header sends "refresh_token" with an empty value, the same flags (HttpOnly, SameSite=Strict, Path=/api/v1/auth) and Max-Age=0, so the browser removes it, and context.cookies() no longer lists it.
3. Given any response of the web app (page or static file) or of the API, When its headers are inspected, Then it carries "X-Content-Type-Options: nosniff" and "Referrer-Policy: no-referrer"; every web app response carries the Content-Security-Policy of ADR-004 (SPA policy) and every API response carries the API policy "default-src 'none'; frame-ancestors 'none'", and every response under /api/v1 carries "Cache-Control: no-store"; and every response of the refresh and logout endpoints, success or error (refresh: 200, 401, 403 and 429; logout: 204 and 403), also carries "Vary: Origin", because their outcome depends on the Origin request header (contract conventions, ADR-004 section 1).
4. Given the API answers with an error, When I cause a 400 (invalid sign-up form), a 401 (no token), a 403 (a member asks for the admin invite link, or a refresh without the guard header), a 404 (another organization's post id) and a 429 (rate limit exceeded), and I also trigger errors that nginx itself generates (a request body over the 64 KB limit on an /api/v1 path giving 413, an unknown path on the web app giving 404, and a proxied 502 when the backend is stopped), Then each of these responses carries the same headers as criterion 3 that apply to it (nosniff and Referrer-Policy always, the SPA CSP on web app paths; nginx must repeat them in every location, ADR-004), every response of the backend carries "Cache-Control: no-store" (the contract and ADR-004 name no-store for backend responses under /api/v1; no-store on the 413 and the 502 that nginx generates itself is ASSUMED), and the body of each backend error is { "error": { "code", "message", "details" } } where the details of a 400 name only the field and the rule, never the value I submitted.
5. Given a run in which a user signs up with the password "Passw0rd!x", logs in, refreshes, logs out and an invite is previewed and accepted, When the application log and the reverse-proxy access log are searched, Then they contain none of: that password, any access token, any refresh token, the values of the Authorization, Cookie or Set-Cookie headers, the exact values of JWT_SECRET and INVITE_TOKEN_KEY, a stored password hash, or any request body of /auth/* and /invites/*; the access log records only method, route template, status and duration (plus request id, user id and organization id when known), and emails are not written in clear in error logs (ADR-004).
6. Given the web app is loaded in a browser and I sign up, log in, create an organization and open the board, When the browser console is read, Then it reports no Content-Security-Policy violation.

## Business rules
- Cookie flags, the empty cookie that clears it and the no-store rule come from the contract (headers RefreshCookie and CookieCleared, conventions) and ADR-002 and ADR-004; "no-store" applies to every response under /api/v1, success and error.
- Never logged: request bodies of /auth/* and /invites/*, the Authorization, Cookie and Set-Cookie headers, passwords, hashes, tokens, JWT_SECRET and INVITE_TOKEN_KEY (ADR-004 section 4). 400 details never contain the submitted value (contract conventions, ADR-004).
- The nginx 413 is not a JSON error body and is not in the contract (accepted risk R14); only its headers are asserted. The 502 case needs a test that stops the backend (ADR-004's header test requests a proxied 502).
- A tester needs access to the application and proxy logs (same setup as F3-2 criterion 2).
