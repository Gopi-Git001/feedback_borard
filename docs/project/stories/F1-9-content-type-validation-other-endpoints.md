# F1-9: A request body that is not JSON is refused on organization create, post create, comment create and status change
Status: READY
Security review: touches authentication (security-bot review required)
As a signed-in user of the feedback board, I want the server to refuse a write request whose Content-Type is not JSON, so that a page on another site cannot send a "simple" cross-site form or text request that changes my organization, posts, comments or statuses without a preflight.

Traces to ADR-004 section 3 (a test per endpoint that takes a body, sending "text/plain" and expecting 415 and no row written), the contract conventions (415 for a request with a body that does not send "application/json"), the TASK-040 follow-up from the Orchestrator (item 5, after the post-merge review of PR #6). Sign-up and login are F1-8 criterion 3; invite preview and accept are F3-4 criterion 3.

## Acceptance criteria
1. Given I am logged in and belong to no organization, When I send "POST /organizations" with a body that would otherwise be valid ({"name": "Acme"}) and a Content-Type whose media type is not "application/json" (test data: "text/plain", "application/x-www-form-urlencoded", "multipart/form-data", no Content-Type, "application/jsonp", "application/jsonx", "text/json", "application/vnd.api+json", "application/json-patch+json", "text/plain; x=application/json", an empty Content-Type value, two Content-Type lines (also "application/json" twice) and a comma-joined value ("application/json, text/plain")), Then each response is 415 with the standard error body (code "VALIDATION_ERROR"), no organization and no membership is created, and I still belong to no organization (an endpoint that needs an organization still answers 403 "ORG_REQUIRED").
2. Given I am an admin or member of "Acme", When I send "POST /posts" with a body that would otherwise be valid (a type, a title and a description within the limits) and a Content-Type from the same test data as criterion 1, Then each response is 415 with the standard error body, no post is created (the board and the post count of "Acme" are unchanged), and when I send the same body as "application/json", "application/json; charset=utf-8" or "APPLICATION/JSON" it is accepted with 201 (only the media type is compared, case-insensitively, parameters ignored).
3. Given I am a member of "Acme" and a post of "Acme" exists, When I send "POST /posts/{post_id}/comments" with a body that would otherwise be valid ({"body": "Thanks"}) and a Content-Type from the same test data as criterion 1, Then each response is 415 with the standard error body, no comment is created (the comment list and the comment count of the post are unchanged).
4. Given I am an admin of "Acme" and a post of "Acme" has the status "New", When I send "PATCH /posts/{post_id}/status" with a body that would otherwise be valid ({"status": "Planned"}) and a Content-Type from the same test data as criterion 1, Then each response is 415 with the standard error body and the status of the post is still "New".
5. Given the four endpoints of criteria 1 to 4, When a request with "text/plain" is sent (a) without any login, (b) with a login that is not allowed to do the operation (a member on the status change; a post id that belongs to another organization or does not exist on the comment and status endpoints), and (c) with a body that would be answered 400 as "application/json" (for example an empty title or an unknown status), Then every one of them is answered 415, not 401, 403, 404 or 400 (the 415 check comes after any IP-keyed limiter and before authentication, lookup and body validation), and nothing changes; and as "application/json" the same requests are answered 401, 404 or 403, and 400 as before.
6. Given I am logged in without an organization and the per-user limit of "POST /organizations" is set small with a long window (RATE_LIMIT_ORG_CREATE_PER_USER, technique of F1-2: N requests let through, then request N+1), When request N+1 is a valid "application/json" request, Then it is answered 429 with "Retry-After" of at least 1; and when a "text/plain" request is sent at that moment, Then it is answered 415, not 429, and does not count toward the per-user limit; and when a request without a login is sent as "text/plain" it is 415 and as "application/json" it is 401, never 429 and no bucket is created; and when the body is invalid as "application/json" after the limit is used up, the answer is 429, not 400 (ASSUMED order for "POST /organizations": 415, then 401, then the per-user 429, then 400, then 409; ADR-004 section 3 and the contract on main state it as an architect decision, ASSUMED, not approved by Gopi; "POST /organizations" has no per-IP limiter, and any IP-keyed limiter elsewhere still runs before the 415); and for post create, comment create and status change, which have no limiter (accepted risk R5, ADR-004 section 7), a 415 is never replaced by a 429.

## Business rules
- A request with a body must send Content-Type "application/json", otherwise 415 with the standard error body (code "VALIDATION_ERROR") and no change. The check is not listed per operation in the contract (like the 413 of nginx) and runs after any IP-keyed limiter and before authentication (contract conventions, ADR-004 section 3); none of the four endpoints has a per-IP limiter.
- Check order for every endpoint (ADR-004 section 3): 429 (IP-keyed limiter), 415 (Content-Type), 401, 400, 404, 409; each endpoint uses the subset that applies. The one user-keyed limiter, the per-user limit of POST /organizations (RATE_LIMIT_ORG_CREATE_PER_USER), needs the caller's identity, so for that endpoint the order is 415, 401, per-user 429, 400, 409 (ADR-004 section 3 and the contract on main, Attempt 9 of TASK-001: architect decision, ASSUMED, not approved by Gopi). The contract orders a protected endpoint as 401, lookup scoped to the organization (404, also for another organization's resource), then role (403).
- Content-Type comparison (source: ADR-004 section 3 and the contract on main, merged with PR #7; ADR-004 itself marks the comparison details ASSUMED, so they stay ASSUMED here): only the media type is compared, that is the part before the first ";", trimmed, case-insensitively; parameters are ignored. "application/json", "application/json; charset=utf-8" and "APPLICATION/JSON" are accepted. Everything else gets 415: "text/plain", "application/x-www-form-urlencoded", "multipart/form-data", no Content-Type, "application/jsonp", "application/jsonx", "text/json", any "+json" type such as "application/vnd.api+json" or "application/json-patch+json", and "text/plain; x=application/json" (a parameter never changes the media type); also an ambiguous header: an empty value, more than one Content-Type line (even two identical lines) or a comma-joined value such as "application/json, text/plain" (ADR-004 section 3, ASSUMED there).
- The contract has no endpoint to update a post or a comment (F4-1: editing posts is after the MVP; F6-1: no comment editing in the MVP), and ADR-004 section 3 on main now says the same: its per-endpoint test covers the eight body-carrying operations (sign-up, login, organization create, invite preview and accept, post create, comment create and post status change). If update endpoints are added, they follow the same rule.
- The endpoints that take no body (refresh, logout, vote toggle, delete post, the GET endpoints, invite link creation) have no Content-Type rule.
