# F1-2: Stay logged in, log out, and rate limits on sign-up, login and refresh
Status: READY
Security review: touches authentication (security-bot review required)
As a user, I want my login to be renewed automatically for up to 7 days and to be able to log out so that the session really ends, and I want repeated automated sign-up, login and renewal attempts to be limited, so that my account stays usable and safer.

Traces to brief feature F1 and to the human-approved additions in brief.md ("POST /auth/refresh and POST /auth/logout ... refresh tokens are stored server-side with rotation and a 7-day absolute cap, and logout revokes them"; "Rate limiting (HTTP 429) on signup, login, refresh and invite preview/accept"). Reuse detection of rotated tokens, the CSRF guard (X-Requested-With and Origin) and the bearer-token rule are in F1-3; the cookie flags, the security headers and the log rules are in F1-4; the logout-versus-refresh race and the session cap are in F1-5.

## Acceptance criteria
1. Given I am logged in and my browser holds a valid refresh cookie, When the app asks for a new access token (for example on page reload, or after my 15-minute access token expired; the request carries the guard header described in F1-3), Then the response is 200, a new access token valid for 900 seconds is issued for the same user, the refresh token is rotated (the cookie is replaced by a new value), the new cookie's Max-Age is the number of seconds left until my login time plus 7 days (never more than 604800), and I stay logged in without typing my password.
2. Given the refresh cookie is missing, tampered with, expired, or its token was already revoked (for example by logout), When the app asks for a new access token, Then the response is 401 with code "UNAUTHENTICATED", the refresh cookie is cleared (Max-Age 0), no access token is issued, and I am shown the login form (ASSUMED UI behaviour); every refresh 401 clears the cookie except the one case of a token rotated less than 10 seconds ago (F1-3 criterion 2, rule in F1-3 Business rules), and a token revoked by logout is never in that case (F1-3 criterion 6).
3. Given I logged in at time T (by sign-up or log-in) and have kept refreshing, When I ask for a new access token at any moment before T plus 7 days, Then it succeeds and the new cookie expires no later than T plus 7 days (a refresh 6 days after T gives a Max-Age of at most 86400 seconds); and when I ask at or after T plus 7 days, Then the response is 401, the cookie is cleared, I am shown the login form, and logging in again starts a new 7-day period. (Test with a controllable clock; ASSUMED test technique.)
4. Given I am logged in and have copied my refresh cookie value, When I log out (the request carries the guard header described in F1-3), Then the response is 204, every refresh token of that login is revoked on the server, the refresh cookie is cleared (Max-Age 0), I am shown the login form, and when my earlier copy of the cookie is sent for a new access token, Then the response is 401 and no access token is issued; and logging out again with no cookie, an unknown cookie or an already revoked one also returns 204, and no logout request is ever answered with 429 (test with 100 logout requests from one IP in a minute; ASSUMED test value).
5. Given one IP address has already made 10 sign-up requests (or 10 login requests) within one 60-second window (ASSUMED threshold: 10 requests per 60-second window per IP per endpoint; window type is an implementation detail and tests must not depend on the boundary), When it makes an 11th request to the same endpoint in that window, Then the response is 429 with code "RATE_LIMITED", the message "Too many requests. Try again later." and a Retry-After header with a whole number of seconds, at least 1 (contract: Retry-After minimum 1), and no account is created or logged in, even if the credentials are valid.
6. Given one IP address has already made 10 token-refresh requests within one 60-second window (ASSUMED threshold, same rule as criterion 5), When it makes an 11th in that window, Then the response is 429 with the same code, message and Retry-After header as criterion 5 and no access token is issued and the refresh cookie is not cleared, and the web app does not treat the 429 as a logged-out session: it does not discard my session or send me to the login form, it shows a "try again later" message and asks again only after the Retry-After seconds, not in an automatic loop (contract: a 429 means try again after Retry-After and the cookie is untouched; the SPA shows a retry-later message that honours Retry-After and does not retry in a loop by itself; contract and ADR-004 mark this as ASSUMED, and so is the message wording); and after the Retry-After seconds have passed, a valid refresh request succeeds as in criterion 1.

## Business rules
- Access token lifetime 15 minutes (900 seconds). The refresh token is an HttpOnly cookie that JavaScript cannot read (API contract, ADR-002).
- Each login or sign-up starts a new token family with an absolute 7-day cap counted from login. Rotation (each refresh replaces the refresh token with a successor in the same family) never extends the session beyond login time plus 7 days. After 7 days I must log in again (contract, ADR-002).
- Logout revokes the whole family on the server, clears the cookie, and is idempotent (always 204). It is not rate limited (contract, ADR-002).
- Known limit, not a criterion (ADR-002, accepted risk R2 and R13): an access token issued before logout or revocation stays valid until it expires, at most 15 min 30 s (15 minutes plus 30 seconds of clock leeway on the token time claims).
- Rate limit (HTTP 429) applies to sign-up, login and refresh, per IP address (contract). Contract-sourced: code RATE_LIMITED, message "Too many requests. Try again later.", Retry-After header in whole seconds, at least 1; the limiter runs before the request is looked at (before the guard header check, authentication and password hashing) and a request is counted whether or not it succeeds (accepted risk R10, ADR-004 section 7). ASSUMED (brief.md): 10 requests per 60-second window per IP per endpoint (window type is an implementation detail and tests must not depend on the boundary), counted separately for each endpoint, configurable by environment variable (RATE_LIMIT_SIGNUP_PER_IP, RATE_LIMIT_LOGIN_PER_IP, RATE_LIMIT_REFRESH_PER_IP, format <max>/<window_seconds>, default 10/60, ADR-002); requests count whether or not they succeed.
- The same 429 rule for invite preview and accept is in F3-1 and F3-2. The limiter under 20 simultaneous requests (exactly 10 pass) is F1-8 criterion 2; the order of checks on invite accept (429 first) is F3-4 criterion 4.

## UI notes
- A "Log out" control for signed-in users (ASSUMED label). Renewal is silent: no screen is shown (ASSUMED).
- A 429 response is shown as a visible "try again later" message (ASSUMED wording; tests may match on the status code instead). On refresh (page load or token renewal) a 429 means "retry after Retry-After": the app keeps the session state and does not show the login form (criterion 6; contract and ADR-004 R10: the SPA must not treat a 429 as a logged-out session). The limiter is off in the e2e run, so this is a component or backend-plus-SPA test.

## Data touched
- Refresh token record kept on the server (only a hash is stored): user, token family, login time (family start), expiry, rotated or revoked state and reason.
- Rate-limit counters (per IP address and endpoint).
- User (read): id, email, display name.

## Out of scope
Rotated-token reuse detection, the CSRF guard header and Origin check, and the bearer-token rule (all F1-3), account lockout and any per-account login limit (out of scope, not offered (Orchestrator decision; the contract on main says "not offered"); accepted risks R1, R3, R4 and R17 in ADR-004 section 7: guessing passwords against one account is limited only by the per-IP limit, passwords have a minimum of 8 and there is no breached-password check (R17), and 10 requests per minute on refresh may lock out several users behind one shared IP address), "log out of all devices", the cap on active families per user (F1-5, ASSUMED in ADR-002), revoking access tokens, password reset, rate limits on other endpoints, CAPTCHA.

## Assumptions / Questions
- ASSUMED: rate-limit threshold 10 requests per 60-second window per IP per endpoint, as in brief.md; window type is an implementation detail and tests must not depend on the boundary. Test technique (ASSUMED, boundary-independent): set a small limit N with a long window through the environment variable of the endpoint (for example 3/3600 in RATE_LIMIT_SIGNUP_PER_IP, RATE_LIMIT_LOGIN_PER_IP, RATE_LIMIT_REFRESH_PER_IP, RATE_LIMIT_INVITE_PREVIEW_PER_IP or RATE_LIMIT_INVITE_ACCEPT_PER_IP), send N+1 requests from one client address, and assert that requests 1 to N are not limited and request N+1 is the first 429, with the format above; after the Retry-After seconds a valid request succeeds. With the long window no window boundary can fall inside the test, and no test needs to know the window type. ADR-002 and the contract on main use the same default (10 per 60 seconds per IP per endpoint, still ASSUMED there) and describe a sliding window; the stories do not depend on the window type. See the TASK-040 handoff, Attempt 3 changes.
- Retry-After at least 1 is contract-sourced (on main; it was ASSUMED in the earliest draft of the contract).
- ASSUMED: "Log out" label, silent renewal, and the redirect to the login form after a failed refresh or logout.

The 429 criteria are therefore backend or component tests with small limits set through the environment variables above.
