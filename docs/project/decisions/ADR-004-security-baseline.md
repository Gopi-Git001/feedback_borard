## Context
The review found that browser hardening, CSRF handling, cache and log rules and the database role were not specified. This ADR is the one place where those cross-cutting rules live; ADR-002 (auth, rate limits) and ADR-003 (invite token) refer to it. It adds no feature and no endpoint.

## Decision

### 1. Response headers
| Header | Value | Where |
|---|---|---|
| `Content-Security-Policy` (SPA) | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` | every response of the frontend nginx |
| `Content-Security-Policy` (API) | `default-src 'none'; frame-ancestors 'none'` | every backend response |
| `X-Content-Type-Options` | `nosniff` | everywhere |
| `Referrer-Policy` | `no-referrer` | everywhere (ADR-003) |
| `Vary` | `Origin` | **every response of `/auth/refresh` and `/auth/logout`, whatever the status** (200, 204, 401, 403, **429**, 500; their outcome depends on the `Origin` request header; security-bot N13 and L-4). The 429 of `/auth/refresh` comes from the rate limiter, before the CSRF guard, and carries both `Retry-After` and `Vary: Origin`. These two endpoints take no body, so they have no 415 (the 415 rule is for body-carrying requests); every response that they do send has `Vary: Origin` |
| `Cache-Control` | `no-store` | **every response under `/api/v1/*`**, success and error (401, 403, 404, 429 too), set by the backend middleware; the SPA's hashed static assets may be cached (`immutable`), `index.html` is `no-cache` |
| `Strict-Transport-Security` | `max-age=31536000` | **only on HTTPS responses**: in the nginx `server` block that terminates TLS (or when a trusted proxy reports `X-Forwarded-Proto: https`), never on plain http, so the local http compose sends no HSTS (a test asserts the header is absent there); no `preload`; `includeSubDomains` only when the operator knows every subdomain is HTTPS-only (not the default) |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` | everywhere |
| `Cross-Origin-Opener-Policy` | `same-origin` | SPA |
- The SPA must work under this CSP: **no inline scripts, no `<style>` elements and no `style="..."` attributes in served or injected HTML** (use CSS classes; `style-src 'self'` blocks them; styles that React applies through the DOM `style` property are set via CSSOM and are not blocked by CSP, but the Playwright console check must prove it, and anything that fails it is not allowed); no third-party scripts, fonts or images. If frontend-bot proves that a library needs inline style attributes, the only allowed relaxation is `style-src-attr 'unsafe-inline'` (decided in a PR, not silently). The Vite dev server needs a looser policy and is for local development only. The Playwright harness must fail a test on any CSP violation in the browser console.
- The backend sets its headers with one middleware; the frontend container sets its own in nginx with `add_header ... always`. nginx passes the backend's `Vary` header through unchanged on `/api/` (it must not set or drop `Vary` there); a test through the compose nginx checks that a 429 of `/auth/refresh` still has `Vary: Origin` and `Retry-After` (run in the TASK-014 e2e job, where the compose nginx and the refresh endpoint both exist; ASSUMED assignment). **nginx `add_header` inheritance:** directives are inherited from the enclosing level only if the current level has no `add_header` of its own, so one `add_header` inside a `location` silently drops all server-level headers there. Therefore the security headers live in one file `security-headers.conf` that is `include`d in **every** `location` (static files, `/api/`, error pages) next to any location-specific header, and a test (devops-bot, qa-bot) requests `/`, a static asset, `/api/v1/health`, a 404 and a proxied 502 and asserts the headers on each.

### 2. XSS and user content
- All user-supplied text (post title and description, comments, display names, organization names) is **rendered as text only**: React's default escaping, **no `dangerouslySetInnerHTML`, no Markdown or HTML rendering**, no URL auto-linking in the MVP. frontend-bot adds a lint rule against `dangerouslySetInnerHTML` (the lint stack is pinned in stack.md; the exact rule is the owner's choice).
- This matters because an XSS bug would still be able to call `POST /auth/refresh` (ADR-002, residual risk).

### 3. CSRF, cookies, CORS
- **Check order (one rule for every endpoint, A5-3):** **429 (rate limiter), 415 (`Content-Type`), 401 (authentication), 400 (body shape), 404 (lookup), 409 (conflict)**. An endpoint uses the subset that applies to it, in the same order: the public body endpoints (signup, login, invite preview) have 429, 415, 400 and, where they have one, 404 or 409; endpoints without a rate limiter start at 415; endpoints without a body skip 415 and 400; endpoints without authentication skip 401; only `POST /invites/accept` has all six. **415 is checked after the rate limiter** (so a flood of wrong-`Content-Type` requests still counts against the client address, R10) and before authentication. **Limiters keyed on the user (Attempt 9, architect decision, ASSUMED, not approved by Gopi):** a limiter keyed on the client IP runs first, before 415, as above. A limiter keyed on the authenticated user id needs the caller's identity, so it can only run **after** 415 and 401 and **before** the 400 and 409 checks: 415 (`Content-Type`), 401 (authentication), 429 (per-user limiter), 400, then 409. The only user-keyed limiter in the contract is the per-user limit of `POST /organizations` (`RATE_LIMIT_ORG_CREATE_PER_USER`, 10 per 60 s); `POST /organizations` has **no per-IP limiter**, so it has only this one, and its order is 415, 401, 429, 400, 409. No other endpoint has a user-keyed limiter (the 10-active-sessions cap is not a limiter and sends no 429; the follow-up write limit of R5 is not in the contract); a future user-keyed limiter follows the same order. Consequences: an unauthenticated request with a wrong `Content-Type` gets 415 (no identity is needed); an unauthenticated request with a good `Content-Type` gets 401 and uses up no user's bucket; the per-user bucket counts every authenticated request that passed 415 and 401, whatever the later 400 or 409 answer is; a request that is answered 415 or 401 is never counted; once the bucket is full the answer is 429 whatever the body or the organization state (an invalid body is not answered 400 and a user who is already in an organization is not answered 409; tests in ADR-002).
- **SPA on 429 (ASSUMED, A3-9(c) with R10):** the SPA shows a retry-later message that honours `Retry-After` and does not retry automatically in a loop; a 429 is never treated as a logged-out session and never clears the cookie.
- **Content-Type (security-bot N13):** every request with a body must send `Content-Type: application/json`; anything else (`text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`, none) gets **415** with the standard error body (`code` `VALIDATION_ERROR`) and no state change; the check runs after any IP-keyed rate limiter and before authentication (check order above; the user-keyed limiter of organization create runs after it). **How `Content-Type` is compared for the 415 rule (A6-3 and security-bot L-1, ASSUMED like the rule itself):** only the media type counts: the part before the first `;`, trimmed of whitespace, compared case-insensitively with `application/json`; parameters are ignored and are never looked at (so a parameter value that contains `application/json` does not help). Accepted: `application/json`, `application/json; charset=utf-8`, `Application/JSON`. 415: `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`, `application/jsonp`, `application/jsonx`, `text/json`, **any `+json` structured-syntax type** (for example `application/vnd.api+json`, `application/json-patch+json`), a header such as `text/plain; x=application/json`, and a missing header. **Empty, repeated and comma-joined values (security-bot A7-1, ASSUMED; one rule: reject what is ambiguous):** a body request is accepted only with exactly one `Content-Type` header line that holds one non-empty media type; an empty value, more than one `Content-Type` header line (even two identical lines) and a value that contains a comma (`application/json, text/plain`) all give 415. The check reads the raw header lines, not a framework's merged value. **How the `Content-Type` value is decoded (Attempt 10, qa-bot A7-1(b); ASSUMED architect decision, not approved by Gopi):** the check reads the raw header bytes and decodes the whole value (media type and parameters) as strict UTF-8. If the bytes are not valid UTF-8 (for example a raw `0xFF` or a Latin-1 `0xE9` byte), the value is undecodable and the answer is 415; there is no Latin-1 fallback and no replacement character, and it does not matter whether the bad byte is in the media type or in a parameter that would otherwise be ignored. A valid UTF-8 value with non-ASCII characters in a parameter (`application/json; x=café`) is decoded and then judged by the media type alone, so it is accepted. **Empty body versus missing header (ASSUMED):** the `Content-Type` is judged before the body is looked at. On a body-carrying endpoint a missing or empty `Content-Type` is 415 even when the body is empty (zero bytes, or `Content-Length: 0`); with `Content-Type: application/json` and an empty body the answer is 400 `VALIDATION_ERROR` (the 400 step, not 415). Endpoints that take no body have no 415: `/auth/refresh` and `/auth/logout` (and every `GET`, `DELETE` and the vote and invite-link `POST`s) do not read the `Content-Type` or the body, so a missing, empty or odd `Content-Type` on them never gives 415. **How the body is decoded after the 415 check (qa-bot's wording, ASSUMED):** the body is decoded as UTF-8 whatever the `charset` parameter says (the parameter is ignored like every parameter); a body that is not valid UTF-8 gives 400 `VALIDATION_ERROR`, never 500 and never a stack trace (this is separate from the lone-surrogate rule of ADR-003, which concerns a valid JSON string). **The body is strict JSON; a UTF-8 byte-order mark (BOM) is not accepted (Attempt 12, qa-bot suggestion 4, made explicit by security-bot P21-1; ASSUMED, not approved by Gopi):** a request body whose first three bytes are `0xEF 0xBB 0xBF` is rejected with 400 `VALIDATION_ERROR` before it is parsed; it is never parsed and never gives 500, whatever the `charset` parameter says. **Backend duty (explicit check):** the framework does not reject a BOM by itself. Python's `json.loads` on bytes accepts and skips it (checked 2026-10-27: `json.loads(b'\xef\xbb\xbf{"a":1}')` returns `{'a': 1}`), and a FastAPI 0.162.0 and Starlette 1.10.0 route with a Pydantic model answered 200 to a BOM body sent as `application/json`. So the backend must check the raw body bytes of every body-carrying operation and reject a body whose first three bytes are `EF BB BF` before it is handed to the JSON parser; the check sits with the global 415 gate and the UTF-8 check, and a BOM in the middle of a body is just invalid JSON (400 by the normal body checks). (RFC 8259 section 8.1 says implementations must not add a BOM and lets a parser ignore one; this rule is the stricter choice.) Stories F1-8 criterion 6, F1-9 criterion 5 and F3-4 criterion 3 carry the test. **The 415 gate is global (Attempt 12, P10-2, ASSUMED):** it applies to every body-carrying operation of the contract with no per-route opt-out and no exemption list, so a new body-carrying operation gets it by default. A route or method that the contract does not define is not an operation: it is answered by routing before the body is read, with **405** `METHOD_NOT_ALLOWED` when the path exists with other methods (with an `Allow` header that lists the methods the path has) and **404** `NOT_FOUND` when the path does not exist (ASSUMED; the standard error body, not the framework's default `detail` body; the two codes are global codes of the contract's error enum, decided in the next paragraph). **Error codes of framework-level answers (Attempt 12, Orchestrator item from qa-bot's review of PR #22, ASSUMED architect decision, not approved by Gopi).** What the backend emits on main (read from `backend/feedback_board/errors.py` and run): every error uses the envelope `{error:{code,message,details:[]}}`; an unknown path gives 404 `NOT_FOUND` ("Not found"); a wrong method gives 405 `METHOD_NOT_ALLOWED` ("Method not allowed") **without an `Allow` header** (the handler drops the framework's header, so backend-bot must copy it; RFC 9110 requires `Allow` on a 405); `GET /api/v1/health` gives 200 `{"status":"ok"}` or 503 `INTERNAL_ERROR` ("Database unavailable"); any other framework `HTTPException` (not 400, 404 or 405) becomes `INTERNAL_ERROR` with its own status. These codes were not in the contract's error enum. **Decision:** (a) every error the backend emits uses the uniform envelope, never the framework's default `detail` body; (b) `NOT_FOUND` and `METHOD_NOT_ALLOWED` are added to the contract's error enum as **global** codes for routing-level answers, not listed per operation (like 415 and nginx's 413); `NOT_FOUND` is used only when no route matches and never for a missing resource: a resource that is missing or belongs to another organization keeps `POST_NOT_FOUND`, an unknown invite token keeps `INVITE_NOT_FOUND`, and their uniform-404 semantics are unchanged (a client must not read `NOT_FOUND` as "the resource is absent"); (c) a 405 carries the `Allow` header; (d) 503 is not a response of the business contract: `GET /api/v1/health` is an operational endpoint outside `api-contract.yaml` (which keeps 15 paths and 18 operations; the TASK-004 question whether to add it to the contract is answered no, ASSUMED), its 503 uses the existing `INTERNAL_ERROR` code with the message "Database unavailable" (no new `SERVICE_UNAVAILABLE` code) and never echoes the connection string or a password; (e) the Argon2 wait-timeout 503 (ADR-002, N5(c), R11) is a different case and stays **not decided: the Orchestrator decides if it is ever taken**; ADR-002's remark that a database outage fails the rate-limit counter with a 503 is not changed here (if taken it uses the same `INTERNAL_ERROR` envelope). **Tests:** an unknown path gives 404 `NOT_FOUND` in the envelope; a wrong method on a defined path gives 405 `METHOD_NOT_ALLOWED` with an `Allow` header; health with the database down gives 503 `INTERNAL_ERROR` and no password in the body; the P10-2 negative test is stated with these codes: `PUT` and `PATCH` on `/posts/{post_id}` give 405 `METHOD_NOT_ALLOWED` with `Allow`, `PUT` and `PATCH` on `/comments/{comment_id}` give 404 `NOT_FOUND`, with `application/json` and with `text/plain`, and never 415. A cross-site page can send only those three simple types without a CORS preflight, so this closes the no-preflight route to every body-carrying endpoint. 415 is not listed per operation (like nginx's 413, R14); **per-operation 415 tests (Attempt 12, security-bot P10-2, ASSUMED):** one automated test on each of the eight body-carrying operations of the contract, `POST /auth/signup`, `POST /auth/login`, `POST /organizations`, `POST /invites/preview`, `POST /invites/accept`, `POST /posts`, `PATCH /posts/{post_id}/status` and `POST /posts/{post_id}/comments`, sends `text/plain` with a body that would be valid JSON and expects 415 with `VALIDATION_ERROR` in the standard envelope and no row written or state changed (for the authenticated ones also with no login, which still gives 415, not 401); the contract has no edit or update endpoint for posts or comments, editing is not in the MVP, and the operations without a body (`POST /auth/refresh`, `/auth/logout`, `/posts/{post_id}/vote` and the `GET` and `DELETE` operations) never answer 415. This is in addition to the global statement above. **Tests (A6-3, L-1), run in full on signup, login, invite preview and invite accept:** accepted, `application/json`, `application/json; charset=utf-8`, `Application/JSON` and `APPLICATION/JSON; Charset=UTF-8` (the request reaches the body checks); 415 with no state change: `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`, `application/jsonp`, `application/jsonx`, `text/json`, `application/vnd.api+json`, `application/json-patch+json`, `text/plain; x=application/json`, and a missing header. Also 415 with no state change: `Content-Type:` with an empty value; two `Content-Type` lines (`application/json` twice, and `application/json` with `text/plain` in both orders); comma-joined values (`application/json, text/plain`, `text/plain, application/json`, `application/json,application/json`); and `text/plain; x=application/json` (a parameter value never counts). **Tests (Attempt 10, qa-bot A7-1(b), ASSUMED), on signup, login, invite preview and invite accept unless stated:** 415 with no state change: a `Content-Type` value that is not valid UTF-8 (`application/json; x=` followed by the byte `0xFF`, `text/plain; x=caf` followed by the byte `0xE9`, and `application/json` followed by the byte `0xFF`); accepted: `application/json; x=café` sent as UTF-8 bytes (it reaches the body checks); a zero-byte body with no `Content-Type` gives 415, a zero-byte body with an empty `Content-Type:` gives 415, a zero-byte body with `Content-Length: 0` and no `Content-Type` gives 415, and a zero-byte body with `Content-Type: application/json` gives 400 (not 415) with the standard error body and no state change; a body with invalid UTF-8 bytes (for example `{"token": "` followed by `0xFF` and `"}`) with `application/json` and with `application/json; charset=iso-8859-1` gives 400, never 500; a valid UTF-8 body with `application/json; charset=iso-8859-1` is decoded as UTF-8 and reaches the body checks. **Tests (Attempt 12, qa-bot suggestion 4, ASSUMED), on signup, login, invite preview and invite accept:** a body that starts with the UTF-8 BOM (`0xEF 0xBB 0xBF` followed by `{"token": "x"}`, with the fields that endpoint needs) with `application/json` and with `application/json; charset=utf-8` gives 400, never 500 and never 200, and no state change (the case that matters is an `application/json` body with a BOM followed by otherwise valid JSON: the parser alone would accept it, so only the explicit first-three-bytes check gives 400). **nginx (N14-5):** the UTF-8, BOM and empty-body tests run against the backend directly, not through the compose nginx; how nginx treats non-ASCII bytes and an empty `Content-Type` header is unverified, and the TASK-014 e2e job, which goes through the compose nginx, must check it (ASSUMED assignment; TASK-007's nginx test covers only the client address and `Vary`). **Undefined edit routes (P10-2, ASSUMED):** `PUT` and `PATCH` on `/posts/{post_id}` (the path exists with `GET` and `DELETE`) give 405 with an `Allow` header that lists `GET` and `DELETE` and not `PUT` or `PATCH`; `PUT` and `PATCH` on `/comments/{comment_id}` and on `/posts/{post_id}/comments/{comment_id}` (no such path) give 404; each with a JSON body and with a `text/plain` body (the 415 gate does not apply to a route the contract does not define); never 200, 204, 415 or 500, and nothing changes in the database. `POST /auth/refresh` and `POST /auth/logout` (tests at TASK-010): with no `Content-Type` and no body, with `Content-Type: text/plain` and with an empty `Content-Type:` they never answer 415 (they reach the CSRF guard and then the cookie logic, as before).
- The refresh cookie is `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. **Refresh 401 cookie rule (one rule; the same case list is in ADR-002, ADR-004, data-model 3.8 and the contract):** a 401 from `/auth/refresh` sends **no `Set-Cookie` in exactly one case**: the presented token's own row has `revoked_reason = 'rotated'` and `revoked_at` is **less than** `REFRESH_REUSE_LEEWAY_SECONDS` (default 10) ago; nothing is changed (two tabs racing, the winning tab's new cookie must survive). **Every other 401 clears the cookie** (`Set-Cookie: refresh_token=; Max-Age=0`): (a) the cookie is missing, or its JWT is invalid, has the wrong `typ` or is expired; (b) there is no row for the token, or its `expires_at` has passed (the 7-day cap included); (c) `revoked_reason = 'rotated'` and `revoked_at` is 10 s or more ago: reuse, every active row of the family is revoked with `reuse_detected` (none if the family is already dead); (d) any other `revoked_reason` (`logout`, `evicted`, `reuse_detected`), **at any time, including within 10 s of `revoked_at`**: the leeway does not apply to it, so it is treated as reuse of a dead family and the answer is 401 with the cookie cleared (the family is already revoked, nothing else changes). The leeway covers **only tokens revoked with reason `rotated`**, and only within 10 s of that `revoked_at`; a token revoked by logout, eviction or reuse detection is never inside it. Tests (full list in ADR-002): two parallel refreshes with the same cookie, the loser gets 401 without `Set-Cookie` and the browser's cookie jar still holds the winner's new cookie; a refresh with a cookie that logout or eviction has just revoked (within 10 s) gets 401 **with** the cleared cookie.
- **Origin check plus custom header on the cookie endpoints** (`/auth/refresh`, `/auth/logout`): `X-Requested-With: feedback-board` is required and a present `Origin` must equal `FRONTEND_ORIGIN` exactly; otherwise 403 `FORBIDDEN`, no state change. **Order of checks on `/auth/refresh`: (1) rate limiter (429), (2) CSRF guard (`X-Requested-With` and `Origin`, 403), (3) cookie, JWT and database logic**; `/auth/logout` has no limiter: guard, then logic. The limiter is first on purpose (every attempt counts, F1-2), so requests that the guard rejects still use up the client IP's quota: accepted risk R10. A non-browser client can send any header, so the guard is a CSRF defence, not authentication. **`Origin: null` is present and unequal, so it gets 403**. Because every response sends `Referrer-Policy: no-referrer`, a browser sends `Origin: null` on a non-GET request whose fetch mode is not `cors` (WHATWG Fetch, "append a request Origin header", checked 2026-10-27): so the SPA must call the API with the default `fetch()` mode `cors` and never `mode: 'same-origin'` or `'no-cors'`, and must not use form posts or navigations for `/auth/*`; a Playwright test must show that refresh and logout from the real SPA are not rejected. (Sandboxed iframes and some cross-origin redirects also send `Origin: null`; a correctly written SPA never does.) `FRONTEND_ORIGIN` must be a bare origin (`scheme://host[:port]`, no path, no trailing slash, validated at startup). All other endpoints use the `Authorization` header (not sent automatically by browsers), so they are not CSRF-prone.
- **The `Secure` flag is on by default.** `APP_ENV` is required and fails closed (ADR-002: unset or not `development`/`test`/`production` means the app does not start). The environment variable `COOKIE_SECURE` (default `true`) may switch it off only when `APP_ENV` is `development` or `test`, for plain-http local development; the app **refuses to start** when `APP_ENV=production` and the flag is off. **This is one case of the fail-closed relaxation guard of ADR-002** (`COOKIE_SECURE=false`, `RATE_LIMIT_ENABLED=false`, a cross-origin dev CORS origin and the weaker Vite CSP are refused at startup unless `APP_ENV` is `development` or `test`, and also whenever `FRONTEND_ORIGIN` is a non-local `https://` origin; one WARNING line per active relaxation is logged; startup tests are listed in ADR-002). There is no runtime switch: the guard cannot be turned off by a request, a header or an admin endpoint.
- **CORS:** the SPA and the API are same-origin through the nginx proxy, so no CORS is needed in compose. If the backend is called cross-origin (local dev), allow exactly `FRONTEND_ORIGIN` (one explicit origin, never `*`), with credentials, methods `GET, POST, PATCH, DELETE`, headers `Authorization, Content-Type, X-Requested-With`.

### 4. Logging and error responses
- Never logged: request bodies of `/auth/*` and `/invites/*`, and the `Authorization`, `Cookie` and `Set-Cookie` headers; passwords, hashes, tokens, `JWT_SECRET`, `INVITE_TOKEN_KEY`. Error tracking (if added) strips bodies and those headers before sending.
- 400 `VALIDATION_ERROR` `details` contain the field name and the rule only, **never the submitted value** (the FastAPI `input` and `ctx` values are dropped when 422 is remapped to 400). The same applies to logs of validation errors.
- Structured access log: method, route template, status, duration, request id; user id and organization id when known. Emails are not written in clear in error logs.

### 5. Database access
- The backend connects as a **non-owner, non-superuser PostgreSQL role** with SELECT, INSERT, UPDATE, DELETE on the application tables and USAGE on sequences if any; no DDL, no `BYPASSRLS`. The backend reads `DATABASE_URL` (the restricted role); Alembic migrations run with a separate owner role given by `DATABASE_MIGRATION_URL` (a one-shot compose service only; the long-running backend container never receives it, accepted risk R18). The compose `db` init creates the restricted role; the owner role is the one the official image creates from `POSTGRES_USER`, which is a PostgreSQL superuser (accepted for the local MVP as R18, with five conditions). The backend must refuse to start when its own role is a superuser or has `BYPASSRLS` (ASSUMED architect addition, R18 condition 3; written where the backend opens its database connection and tested at TASK-006 with the real roles).
- Row-Level Security is **scheduled** as the next hardening step (data-model.md section 1): with a non-owner role in place, `ENABLE ROW LEVEL SECURITY` plus a policy on `organization_id = current_setting('app.organization_id')::uuid` per tenant table and `SET LOCAL app.organization_id` per transaction can be added without changing the API. Not in the MVP.
- Tenant checks: authentication (401), then lookup scoped to the organization (404 for another organization's rows), then role (403), on **every** endpoint that takes a post id, including sub-resources `/posts/{id}/vote`, `/posts/{id}/comments`, `/posts/{id}/status` and `DELETE /posts/{id}` (conventions in api-contract.yaml).

### 6. Accounts and passwords (what is and is not done)
- Minimum 8 characters stays (story F1-1); maximum 128; Argon2id (ADR-002). **Not met, follow-ups:** the minimum is below NIST SP 800-63B-4 section 3.1.1.2 (15 characters when the password is the only factor, 8 allowed only as part of multi-factor authentication; this app is password-only; OWASP ASVS 5.0.0 6.2.1 requires 8 and recommends 15, so 8 meets the ASVS minimum), there is no password blocklist (ASVS 6.2.4, top 3000, level 1) and no check against breached-password lists (ASVS 6.2.12, level 2), and there is no password change, reset or email verification flow (no emails in the MVP). When a change or reset flow is added it must revoke all refresh-token families of the user.
- `409 EMAIL_TAKEN` on signup is required by story F1-1 and is an enumeration oracle; mitigated by the per-IP signup limit only (ADR-002), which allows 10 signup requests per 60 s per IP, about 14,400 probes per IP per day (10 x 1,440 minutes per day = 14,400; more with many IPs). The limit was 5 per 3,600 s in attempt 2 and is 10 per 60 s since attempt 3 (the approved rule); any older 5-per-hour wording is superseded. A generic response would contradict the story and is not done.
- Rate limits, counter store, proxy trust and the env vars that tune them: ADR-002 (10 requests per 60 s per IP per endpoint by default, rolling window). ### 7. Known limits (accepted risks, not fixed in the MVP)
- **No rate limit on authenticated writes** (posts, comments, votes, status changes, deletes): the approved scope (brief, F1-2) limits only signup, login, refresh, invite preview/accept (plus the architect-added organization create). **The impact is platform-wide, not limited to the writer's organization:** all tenants share one database and anyone can sign up (no email verification), so a script that creates accounts and writes as fast as the server allows threatens availability and storage for every organization. Follow-up: nginx `limit_req` or a per-user write limit using the same `rate_limit_hits` table. Register row R5 (R12 is merged into it).
- **Request body size:** nginx sets `client_max_body_size 64k` (ASSUMED; the largest legitimate body is a 2000-character description, at most about 8 KB in UTF-8 plus JSON) so the backend never buffers large bodies. Over-size requests get nginx's 413, which is not a JSON error body and not in the contract; the SPA treats any non-2xx as an error. Pydantic field limits (contract) apply inside that size. Register row R14.
- Access tokens stay valid until they expire after logout, reuse detection or eviction (at most 15 min 30 s: 15 min lifetime plus the 30 s JWT leeway), ADR-002. Register rows R2 and R13.

## Consequences
- Easier: one checklist for backend-bot, frontend-bot, devops-bot and qa-bot; each rule is testable (header assertions, CSP-violation check in Playwright, log-content tests, startup refusal tests).
- Harder: the CSP rules out inline styles and third-party assets; two database roles must be provisioned; the SPA must send the CSRF header on refresh and logout.
