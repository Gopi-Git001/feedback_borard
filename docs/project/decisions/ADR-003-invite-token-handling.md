# ADR-003: Invite token handling (URL fragment, POST body, derived token, log hygiene)
Status: Proposed (rewritten in attempt 2b after the security-bot review of PR #2, blocker 2 and should-fix 3; **supersedes** the Attempt 2 decision "keep the token in the URL path and redact it in logs")
Date: 2026-10-27   Deciders: architect-bot (proposes), Orchestrator (approves); security-bot to re-review
Attempt 3 (qa-bot review of attempt 2, Must-fix 3): the key-rotation rule below is corrected (the admin endpoint now updates the stored hash, and lookup rechecks it against the current key). **security-bot must confirm this rule.**

## Context
Story F3-1: each organization has **one persistent invite token**, the admin sees the same link every time, it is long and random (at least 32 characters) and reusable. The token is a **bearer secret**: whoever holds it can join the organization as a member.

Attempt 2 kept the token in the URL path (`/invite/<token>`, `GET /invites/{token}`, `POST /invites/{token}/accept`) and relied on log redaction. The security review rejected that (blocker 2): the token still reaches uvicorn and proxy logs, error tracking and `Referer` if any one redaction is missed, and because the token is permanent and cannot be revoked, one leak is permanent. It also asked not to store the token in clear (finding 3).

## Options considered
Where the token travels:
1. Path or query (Attempt 2). **Rejected:** every server, proxy and tool on the path sees it by default.
2. **URL fragment for the link, POST body for the API (chosen).** The browser never sends a fragment to any server and never puts it in `Referer`; the SPA reads it and sends it in a JSON body, and request bodies are not logged by default.
3. Custom header from the SPA. Equivalent for logs, but a JSON body is simpler for the contract and for tests; not chosen.

How the token is stored (F3-1 forbids a different link on each click, so a salted hash alone cannot work):
1. Plaintext column (Attempt 2). **Rejected:** a database dump or backup reveals working links.
2. Encrypted copy with a separate key. Works, but stores a reversible secret and needs a nonce and key handling.
3. **Derived token, only its hash stored (chosen).** `token = base64url(HMAC-SHA256(INVITE_TOKEN_KEY, "invite:v" + token_version + ":" + organization_id))` without padding (43 characters, 256 bits). Exact input: `token_version` as decimal ASCII digits (no leading zeros) and `organization_id` as the canonical lowercase hyphenated UUID text (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`, 36 characters), the key as the raw bytes decoded from `INVITE_TOKEN_KEY` (ADR-002 secret rule). The database stores only `sha256(token)` in `invites.token_hash` plus `token_version`. The admin endpoint recomputes the token on demand, so the same link is shown every time; a database leak alone gives nothing usable. Bumping `token_version` would later give "regenerate link" with no schema change.

## Decision
Option 2 for transport and option 3 for storage.

**Link and API**
- The shareable link is `<frontend-origin>/join#<token>`. `POST /organizations/current/invite` (admin, get-or-create) returns `{token, created_at}`; the SPA builds the link.
- `POST /invites/preview` (public) and `POST /invites/accept` (signed in, no organization yet) take `{"token": "..."}` in the body. **No token in any path or query, ever.**
- Malformed, wrong-length, unknown and old-key tokens (any string, of any length) all give the uniform 404 `INVITE_NOT_FOUND` (message `Invite link is invalid`), so nothing distinguishes the cases (story F2-1 criterion 4). **There is no length limit on the token** (the body schema is `{token: string}` with no `maxLength`; the request size is capped only by nginx, ADR-004 section 7). The one exception is the request shape: a body without a `token` field, with a `token` that is not a string, or with any extra field besides `token` (the request schema has `additionalProperties: false`), gives 400 `VALIDATION_ERROR` (field name and rule only; validation never echoes the value). The contract lists both responses on `POST /invites/preview` and `POST /invites/accept`.
- Lookup is `WHERE token_hash = sha256(token)` (unique index). The value has 256 bits of entropy, so lookup timing is not a practical oracle. Preview and accept are each limited to 10 requests per 60 seconds per client IP (ASSUMED, as in the stories F1-2/F3-1 and ADR-002); a request counts before the token is looked at, so malformed and unknown tokens count too.

**Server-side requirements (backend-bot, devops-bot; qa-bot tests them)**
- `INVITE_TOKEN_KEY`: a new secret, same startup rule as `JWT_SECRET` (decodes to at least 32 bytes, ADR-002), different from `JWT_SECRET`, never in the database, repo or logs. Anyone who has this key and an organization id can compute that organization's link, so it is as sensitive as `JWT_SECRET`.
- **Key rotation (corrected in attempt 3).** The stored `token_hash` is what makes a link work, so rotating the key does nothing by itself unless the hash is refreshed. Rules:
  1. `POST /organizations/current/invite` locks the organization's invite row (`SELECT ... FOR UPDATE`), recomputes the token with the *current* key and the stored `token_version`, and if `sha256(token) <> invites.token_hash` it runs `UPDATE invites SET token_hash = :new_hash WHERE organization_id = :org` in the same transaction before answering. The admin then sees the new link and the new hash is the only valid one (`token_version` is not changed by a key rotation; it changes only for a future "regenerate link"). Concurrent admins compute the same value, so the update is idempotent; the row lock makes it safe. If no row exists, the row is created (get-or-create as before, with `ON CONFLICT (organization_id) DO NOTHING` and a re-read, so concurrent first calls still yield one invite).
  2. `POST /invites/preview` and `POST /invites/accept` find the row by `token_hash = sha256(token)` as before **and then recompute the expected token from the row's `organization_id` and `token_version` with the current key and compare it with the submitted token in constant time; a mismatch is 404 `INVITE_NOT_FOUND`**. Because of this, links issued under the old key stop working the moment the key is rotated (even before any admin opens "Invite"), and the new link starts working as soon as an admin has opened "Invite" once (rule 1 stores its hash). Between those two moments no link for that organization works; that is deliberate.
  3. Several backend replicas must be rotated to the same key together; a replica with the old key would recompute the old token and flip the hash back on the next admin call. Rotation is therefore a stop-and-restart of all backend containers with the new value.
  4. Rotating the key does not touch `JWT_SECRET`, refresh tokens or sessions.
- **Test key denylist (A3-7).** The published test vector key (the 32 bytes `00 01 02 ... 1f`, `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8`) passes the JWT_SECRET-style checks (32 distinct bytes), so startup has an explicit denylist: **compare the decoded bytes** (never the text, so a padded or re-encoded spelling is caught), and refuse to start with `APP_ENV=production` when the decoded key equals the test key (or `JWT_SECRET`, or all bytes equal). Tests: the test key with `APP_ENV=production` exits non-zero; `AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8=` (padded) is also refused; a random key starts; the vector test itself runs with `APP_ENV=test`.
- **Key bytes (attempt 3).** `INVITE_TOKEN_KEY` is unpadded base64url text (the same rule as `JWT_SECRET`, ADR-002). The HMAC key is **the raw bytes obtained by decoding that text** (`base64.urlsafe_b64decode(v + '=' * (-len(v) % 4))`, at least 32 bytes), never the ASCII text itself and never `.encode()` of the string; the message is the UTF-8 bytes of `"invite:v" + token_version + ":" + organization_id` and the digest is SHA-256. Generate with `python -c "import secrets,base64; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).rstrip(b'=').decode())"` (43 characters). The key differs from `JWT_SECRET` (startup check) and is stored only in the secret store or `.env`, never in the database.
- **Rotation runbook (operator; written for the README by docs-bot).** (1) Generate a new key with the command above and keep the old one until step 5. (2) Plan a short window: after step 3 no invite link works until each organization's admin has opened "Invite" once. (3) Stop **all** backend containers, set the new `INVITE_TOKEN_KEY`, start them all (a mixed fleet would flip hashes back and forth, rule 3). (4) Check: an old link gives 404 on preview, an admin's "Invite" shows a different link, and that new link previews and accepts. (5) Destroy the old key. (6) Tell the admins to share the new link again. To roll back, repeat the runbook with the old key (links of the old key work again after an admin opens "Invite"). If the key leaked, run it at once; nothing in the database needs to change by hand. **Notes (A3-8):** (i) a mixed fleet is also a leak window: a replica still holding the old key accepts and re-derives the old (possibly leaked) link, and an admin's "Invite" on that replica restores the old hash, so no replica may run during the rotation with the old key (stop all, then start all); (ii) **never roll back to a leaked key:** a deployment rollback (image, `.env` or secret-store version) that restores the old key makes every leaked link valid again, which is why step 5 destroys the old key; after a leak, a rollback means generating a third key and running the runbook again.
- **Bodies are never logged:** the access-log middleware records method, route template, status and duration only; the bodies of `/api/v1/invites/*` and `/api/v1/auth/*` and the `Authorization`, `Cookie`, `Set-Cookie` headers are never logged, and error-tracking hooks drop request bodies and those headers. The 422-to-400 remapping must not copy the offending `input` value into the response or the log.
- **Reverse proxy (nginx):** access-log format without `$request_body`, `$http_authorization`, `$http_cookie`. (The token is not in `$request_uri` any more; this is defence in depth.)
- **Responses:** all invite responses (`POST /invites/preview`, `POST /invites/accept`, `POST /organizations/current/invite`) carry `Cache-Control: no-store`.
- **Referrer:** the SPA is served with `Referrer-Policy: no-referrer` (response header and `<meta name="referrer" content="no-referrer">`), and the `/join` page loads no third-party resources (CSP, ADR-004). A fragment is not sent in `Referer` in any case; the policy is a second layer.

**SPA requirements (frontend-bot) - fragment handling (extended in attempt 3)**
- The first script that runs on `/join` reads `location.hash`, validates the shape (`^[A-Za-z0-9_-]{43}$`; anything else is treated as invalid without a request), **immediately removes the fragment** with `history.replaceState(null, '', location.pathname + location.search)` (replace, never push, so the token does not stay in the history entry or in screenshots) and keeps the token in memory only (a module variable, not React state that is logged by dev tools, not a route parameter, not `window.name`).
- The token is never put in a URL, a query string, a route state object, an error message, a console log, `document.title`, or any analytics call; no third-party script exists on the page (CSP, ADR-004). The `hashchange` event is ignored after the first read.
- If the visitor is logged out, the token is kept in `sessionStorage` under one key (`pending_invite`) while they sign up or log in, then `/join` resumes; the key is deleted after accept succeeds or fails, on logout, and when the user chooses another action. This is the one deliberate use of Web Storage; it holds only an invite token (the access token never goes to storage, ADR-002). If the visitor is already logged in, nothing is stored: a reload of `/join` after the fragment was removed shows "Invite link is invalid" and the visitor opens the link again.
- The "Join with invite link" choice (story F2-1) accepts a pasted link: the SPA extracts the part after `#` from the pasted text, applies the same shape check and never sends the pasted URL anywhere.
- Show "Invite link is invalid" for any 404 from preview or accept.

**Invite request tests (attempt 5, for backend-bot and qa-bot; each is an automated test).** (i) Missing `token` field, `{}`, `token: null`, `token: 123` and `token: []` give 400 `VALIDATION_ERROR` on both preview and accept, and an extra field (`{"token": "x", "a": 1}`) gives 400. (ii) An odd string gives the uniform 404 `INVITE_NOT_FOUND`: empty string, 1 character, 43 characters of the wrong alphabet, 50,000 characters (under the nginx limit of 64k bytes; a body over that limit gets nginx's non-JSON 413, ADR-004 section 7), whitespace, `../`, a quote or SQL text, an emoji, a NUL character (`\u0000`). (iii) **A lone surrogate (`"\ud800"`) is valid JSON and a valid Python `str` that cannot be encoded as UTF-8: it must give 404, never 500.** The hash step must not call a strict `token.encode()` on unvalidated input; encode with an explicit policy (for example catch `UnicodeEncodeError` and answer 404) and test it. (iv) Malformed JSON (`{`), a body that is not an object (`[]`, `"x"`, `null`), an empty body and deeply nested JSON (for example 10,000 nested arrays, under 64k) give 400 `VALIDATION_ERROR`, never 500 and never a stack trace. A request whose `Content-Type` is not `application/json` (`text/plain`, a form type, none) gets 415 with the standard error body and no state change (ADR-004 section 3, security-bot N13). The request model uses a strict string (`StrictStr`, so `123` is not coerced) and forbids extra fields (`extra='forbid'`), A4-3. (v) **Check order on `POST /invites/accept`: 429 (limiter, before the body is read), then 415 (`Content-Type` is not `application/json`), then 401 (no or bad access token), then 400 (body shape), then the token lookup (404 `INVITE_NOT_FOUND`) and only then the membership check (409 `ALREADY_IN_ORGANIZATION`).** The same order is used everywhere (429, 415, 401, 400, 404, 409; an endpoint uses the subset that applies, ADR-004 section 3 and the contract). A test per step: the 11th request in 60 s with `Content-Type: text/plain` gives 429 (not 415), so a wrong-`Content-Type` request counts against the limiter; an anonymous request with `Content-Type: text/plain` gives 415 (not 401); an anonymous request with a bad JSON body gives 401 (not 400); an authenticated request with a bad body gives 400 (not 404); an authenticated request with an unknown token while already in an organization gives 404 (not 409); the 11th request in 60 s gives 429 whatever the body. On `POST /invites/preview` (public, so no 401 and no 409): 429, then 415, then 400, then 404; tests: the 11th request gives 429 whatever the `Content-Type`, `text/plain` with a bad body gives 415 (not 400), a bad body gives 400 (not 404). (vi) No response and no log line echoes the submitted value.

**Tests (qa-bot; the key-rotation tests (a) and (b) are R7 checkpoint G3 at TASK-017, on a real PostgreSQL):** (a) key rotation: create the invite with key A and keep the link; restart the app with key B; the old link gives 404 on preview and accept; the admin endpoint returns a *different* token; the new link previews and accepts; calling the admin endpoint again returns the same new token (no further change); `invites.token_hash` equals `sha256(new token)` and the row count is still one; (b) concurrency: two admin calls in parallel after a rotation return the same token; (c) HMAC input vector: for a fixed key, `token_version=1` and a fixed UUID, the token equals the vector computed here (key = the 32 bytes `00 01 02 ... 1f`, i.e. `INVITE_TOKEN_KEY=AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8` in unpadded base64url; this value is for tests only and must never be used outside tests; `organization_id=00000000-0000-4000-8000-000000000001`, `token_version=1`): token `PNqzMLttQPIF8nHKGWLPGIMzyUHw8lLpXulro9uECFo`, `token_hash` `bc4debf5f218992063f53085e8e5d0b67f7d685916c9bb5810c398da541780a1`; (d) call the invite endpoints and assert that neither the captured application log nor the proxy log contains the token string or a request body; assert `Cache-Control: no-store`; assert that no request URL in the Playwright trace contains the token.

## Consequences
- Easier: the token cannot appear in a server-visible URL, so one missed log filter no longer leaks it; a database dump gives no usable links; F3-1 behaviour (the same link every time) is kept.
- Harder: preview becomes a POST for a read (documented; no side effects); stories F2-1, F3-1, E2E-1 change their link text and flow (handoff lists them); the SPA needs a small pending-invite flow; one more secret (`INVITE_TOKEN_KEY`) to provision.
- **Residual risk, not fixed (product scope, F3-1, decided by the Orchestrator):** the link is permanent and reusable, there is **no expiry, no revoke, no regenerate and no remove-member** in the MVP. Anyone who obtains the link (chat, browser history before the fragment is stripped, shared screen) can join as a member forever and an admin cannot undo it. Follow-ups in order of value: (1) an admin "regenerate link" (bump `token_version`, one endpoint), (2) expiry, (3) remove member (needs a design for the member's posts, comments and votes; the composite FKs are `ON DELETE NO ACTION`, data-model.md section 4).
- If `INVITE_TOKEN_KEY` leaks together with organization ids, links can be recomputed; the fix is rotating the key (rules above: old links die at once, the admin endpoint stores the new hash). If the team prefers fully random stored tokens, the fallback is a plaintext or encrypted `token` column (Attempt 2 design plus encryption); say so and I will revise.
