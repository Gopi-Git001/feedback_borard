# ADR-002: Password hashing (Argon2id) and JWT approach
Status: Proposed (attempt 3: rate limits aligned to the approved 10 per 60 s per IP, per-account limit removed, per-family locking, APP_ENV fail-closed; revised in attempt 2b after the security-bot review of PR #2; the refresh-token section **reverses** the Attempt 2 decision "stateless refresh tokens, no revocation in the MVP")
Date: 2026-10-27   Deciders: architect-bot (proposes), Orchestrator (approves)

## Context
Brief: built-in email/password, passwords hashed, JWT auth, multi-tenant by organization (one org per user for the MVP), tenant isolation enforced on every query. No external auth services. Security-bot and backend-bot need exact parameters. The tenant must come from the token, never from a request field.

## Options considered
Password hashing (choose one):
1. **argon2-cffi 25.1.0 (Argon2id).** Winner of the Password Hashing Competition, standardised in RFC 9106; library ships ready-made RFC 9106 profiles and `check_needs_rehash`. Cons: last release 2025-06-03 (older than 12 months, but repository active 2026-10-01); native extension (wheels exist for cp314).
2. **bcrypt 5.0.0.** Mature, simple. Cons: 72-byte input limit, not memory-hard, also older than 12 months (2025-09-25).
JWT:
1. **PyJWT 2.15.1**, HS256 symmetric. Small, maintained (release 2026-09-28), enough for a single backend that both signs and verifies.
2. RS256/EdDSA asymmetric. Not needed: there is one service, no third-party verifier. Reconsider if a second service must verify tokens.
Refresh-token state:
1. **Server-side token families in PostgreSQL (chosen, attempt 2b):** only a hash is stored; rotation on every use, reuse detection, logout revokes, absolute 7-day cap. Needs one table and one lookup per refresh (not per request).
2. Stateless 7-day JWT (Attempt 2). Rejected after the security review: a stolen token stays valid for 7 days, every refresh issued another stateless 7-day token while the old one stayed valid, and logout could not revoke anything.
Browser token storage:
1. Access token in JS memory + refresh token in an HttpOnly cookie (chosen).
2. Both in `localStorage`: simplest but any XSS can steal long-lived credentials. Rejected.

## Decision
**Password hashing: Argon2id via argon2-cffi ~=25.1.0.**
- Use `argon2.PasswordHasher.from_parameters(argon2.profiles.RFC_9106_LOW_MEMORY)`, i.e. Argon2id, time_cost=3, memory_cost=65536 KiB (64 MiB), parallelism=4, 16-byte random salt, 32-byte hash (the profile values; verified by running argon2-cffi 25.1.0 on 2026-10-27: `Parameters(type=ID, version=19, salt_len=16, hash_len=32, time_cost=3, memory_cost=65536, parallelism=4)`, five hashes took 40-65 ms each on the architect box; docs: "Choosing Parameters"). Backend-bot must confirm in its first test that one hash takes roughly 50-300 ms in the docker container and report if not; do not lower parameters without a new ADR.
- Store the encoded string (it embeds algorithm, parameters and salt) in `users.password_hash`. On successful login call `check_needs_rehash()` and re-hash if parameters changed.
- Password policy: min 8, max 128 characters (min 8 follows story F1-1). No composition rules, so longer passphrases are possible and encouraged in the UI; reject values over 128 (prevents hash-DoS). Never log or return the password or hash. **Not met, recorded honestly:** NIST SP 800-63B-4 asks for at least 15 characters for single-factor passwords (8 only when the password is one factor of MFA); OWASP ASVS 5.0.0 requirement 6.2.1 requires at least 8 and strongly recommends 15 (so 8 meets 6.2.1), but ASVS 6.2.4 (level 1, a check against at least the top 3000 passwords) and 6.2.12 (level 2, breached passwords) are not met; F1-1 fixes 8, and there is no password blocklist or breached-password check and no reset/change/email-verification flow in the MVP. These are follow-ups (ADR-004, handoff), not decided here.
- **Argon2 concurrency cap:** each hash needs 64 MiB, so a worker runs at most `ARGON2_MAX_CONCURRENCY` (default 4, i.e. at most 256 MiB of hashing memory per worker) hashes at once (semaphore around the thread-pool call); further requests wait. Combined with the per-IP limits below this bounds memory use under a login flood. Size container memory as `workers x 256 MiB` plus the application.
- Login must run `verify` against a dummy hash when the email is unknown, so timing does not reveal which emails exist. Error is always `INVALID_CREDENTIALS` (401).

**JWT: PyJWT ~=2.15.1, algorithm HS256 only** (the decode call must pass `algorithms=["HS256"]`; never read the algorithm from the token header).
- Secret: `JWT_SECRET` environment variable. **One rule, checked at startup (same rule for `INVITE_TOKEN_KEY`, ADR-003, which must also differ from `JWT_SECRET`):** the value must (a) be **unpadded base64url** (alphabet `A-Za-z0-9_-`, no `=`) that **decodes to at least 32 bytes** (`base64.urlsafe_b64decode(v + '=' * (-len(v) % 4))`; in practice 43 or more characters, and a length of 1 mod 4 is invalid), (b) contain at least 16 distinct characters, and (c) not contain, case-insensitively, any known weak or placeholder fragment: `secret`, `changeme`, `change-me`, `change_me`, `password`, `replace`, `placeholder`, `example`, `default`, `jwt`, `test`, `dev` (and the value must not be empty). The app **refuses to start** (exit non-zero, error message without printing the value) if any check fails. Generate with `python -c "import secrets; print(secrets.token_urlsafe(48))"` (64 characters, 48 random bytes; a random value is rejected by (c) with a probability of well under 1%, in which case generate another). The checks reject lazy and placeholder values only; they cannot prove randomness, so the generation command is part of the rule. `.env.example` holds the non-random placeholder `REPLACE_WITH_OUTPUT_OF_secrets_token_urlsafe_48`, which fails the check on purpose (it contains `REPLACE` and `secrets`; it is the check (c) that rejects it, not (a)). CI generates a fresh random value at the start of each job (a test-only value must pass the same check). In any non-local deployment the value comes from the platform's secret store, never from a committed file. Never in code, docs, git or logs. Docker compose reads it from a git-ignored `.env`.
- **Rotation (follow-up, not MVP):** tokens carry no `kid`, so rotating the secret logs everyone out (acceptable at MVP scale). If zero-downtime rotation is needed, add a `kid` header and a list of accepted keys in a new ADR.
- **`APP_ENV` is required and fails closed (attempt 3).** There is no default. The app refuses to start when `APP_ENV` is unset, empty or not exactly one of `development`, `test`, `production`. Every relaxation (`COOKIE_SECURE=false`, `RATE_LIMIT_ENABLED=false`, a cross-origin dev CORS origin, the weaker Vite CSP) is allowed only when `APP_ENV` is `development` or `test`; `.env.example` sets `APP_ENV=development` and the production compose file sets `production`, so a forgotten variable can never switch protections off silently.
- **Access token:** lifetime **15 minutes**, `typ=access`. Sent as `Authorization: Bearer <token>`. Kept in JS memory only (never `localStorage`/`sessionStorage`). After logout or a reuse detection an already issued access token stays valid until it expires (max 15 minutes): accepted, because the role and the membership are read from the database on every request and no access-token denylist is kept.
- **Refresh token (revised in attempt 2b, DB-backed, supersedes "stateless, no revocation"):** a JWT with `typ=refresh` and **no `org` claim**, set as cookie `refresh_token`: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`; `Max-Age` = seconds left until `login time + 7 days`. `Secure` may be switched off only with `COOKIE_SECURE=false` and `APP_ENV` explicitly `development` or `test` (the app refuses to start with `APP_ENV=production` and the flag off). The SPA never reads it. Its `jti` is a random 256-bit value and **only `sha256(jti)` is stored** in table `refresh_tokens` (data-model.md 3.8). Rules:
  - **Family and absolute cap:** login and signup start a new *family*. `family_started_at` is the login time and is copied to every token of the family, and every token expires at `family_started_at + 7 days`: rotation **never extends the session beyond 7 days from login**. After that the user logs in again.
  - **Rotation:** `POST /auth/refresh` verifies the JWT (`typ=refresh`), looks up the hash, marks the token `rotated` (`revoked_at`, `replaced_by`), inserts the successor in the same family and returns a new access token. The `org` claim of that access token is re-read from `memberships`, not copied.
  - **Reuse detection:** presenting a token that is already rotated or revoked revokes **every token of its family** (`reuse_detected`) and answers 401, so a thief and the real user cannot both keep a session. A leeway of `REFRESH_REUSE_LEEWAY_SECONDS` (default 10) after a rotation answers 401 **without** revoking the family, because two browser tabs may race; the SPA also serialises refresh across tabs (Web Locks API, a single-flight refresh), so the leeway is a safety net.
  - **Concurrency: one lock per family (attempt 3, security-bot should-fix N1).** A rotation inserts a *successor* row that a concurrent revoke cannot see or lock, so a logout racing a refresh could leave a live session. Therefore every operation that rotates or revokes a family first takes `SELECT pg_advisory_xact_lock(hashtextextended('rt_family:' || :family_id, 0))` (a transaction-scoped advisory lock; no schema change, and a family row would work the same). **Isolation level: READ COMMITTED (the PostgreSQL default), required for these transactions**, because each statement then gets a fresh snapshot and, after the lock is granted, sees everything the previous holder committed (REPEATABLE READ or SERIALIZABLE would keep the old snapshot and defeat the lock). Procedure: refresh = verify the JWT, find the row by `token_hash` without locking to learn `family_id`, take the family lock, **re-read the row `FOR UPDATE`**, then run rotation or reuse detection; logout = find the family the same way, take the lock, then `UPDATE refresh_tokens SET revoked_at = now(), revoked_reason = 'logout' WHERE family_id = :f AND revoked_at IS NULL`, which sees a successor committed by an in-flight refresh and revokes it; reuse detection and cap eviction revoke all active rows of a family under the same lock. Login and signup additionally take `pg_advisory_xact_lock(hashtextextended('rt_user:' || :user_id, 0))` first (so two concurrent logins of one user cannot both pass the cap check); the lock order is always user lock, then family lock, and refresh and logout take only the family lock, so there is no lock cycle and no deadlock. **Test requirement (qa-bot, backend-bot):** (a) logout vs refresh: run `POST /auth/refresh` and `POST /auth/logout` with the same cookie concurrently (two connections, a barrier, repeated at least 50 times, plus one run with a test hook that delays the refresh transaction between inserting the successor and committing); afterwards, whenever logout answered 204, `count(*) WHERE family_id = :f AND revoked_at IS NULL` is 0 and the cookie issued by the refresh that won gets 401 on its next refresh; (b) reuse vs refresh: presenting an already rotated token while its successor is being rotated ends with no active row in the family; (c) cap: 12 concurrent logins of one user leave at most 10 active families, the surplus ones with `revoked_reason = 'evicted'`; (d) no test hits a deadlock error.
  - **Logout:** `POST /auth/logout` revokes the whole family (`logout`, under the lock above) and clears the cookie; it is idempotent (204 without or with an unknown cookie) and is **not rate limited**.
  - **CSRF guard on both cookie endpoints** (in addition to `SameSite=Strict`): header `X-Requested-With: feedback-board` is required and a present `Origin` must equal the configured frontend origin (`FRONTEND_ORIGIN`) byte for byte, else 403 `FORBIDDEN` with no state change; **a present `Origin: null` (sandboxed iframes, some cross-origin redirects) is not equal and gets 403**, and an absent `Origin` is accepted only because the custom header is still required (a cross-site page cannot add `X-Requested-With` without a CORS preflight, which ADR-004 denies) (ADR-004).
  - **At most 10 active families per user (ASSUMED, an architect addition; not in the stories or the brief, listed in the handoff as an extra).** An *active family* is one with at least one row that is not revoked and not expired. Login and signup also revoke the family of a `refresh_token` cookie presented with the request when its JWT verifies (`revoked_reason = 'logout'`, under the user lock and then that family's lock), so re-logging in in the same browser does not stack sessions (security-bot N4). In the same transaction that creates the 11th family (login or signup, under the user lock), the active family with the lowest `family_started_at` (ties: lowest `family_id`) is revoked: every active row gets `revoked_reason = 'evicted'`. That session gets 401 on its next refresh and must log in again (the contract says so on login and signup); its already issued access token stays valid for at most 15 minutes (the same accepted limit as logout). Evicted rows are kept until the normal cleanup.
  - **These two endpoints go beyond story F1-1** (F1-1 lists logout and session expiry as out of scope); they are approved per Orchestrator message 2026-10-27, relayed from the human, and are marked as extras (`x-extra: true`) in the contract. The SPA calls refresh on page load and on a 401.
- **Claims:** `sub` (user id, UUID string), `org` (organization id UUID string, **absent** until the user creates or joins an organization; access tokens only), `typ` (`access` or `refresh`), `iat`, `exp`, `jti` (random; for a refresh token it is the server-side identifier above), `iss` = `feedback-board`, `aud` = `feedback-board-api`. Verification is exactly: `jwt.decode(token, JWT_SECRET, algorithms=["HS256"], issuer="feedback-board", audience="feedback-board-api", leeway=30, options={"require": ["exp", "iat", "sub", "iss", "aud", "typ", "jti"]})`, then check `typ`: **`access` on every API endpoint** (so a refresh token can never be used as a bearer token) and `refresh` only for the cookie on `/auth/refresh` and `/auth/logout`. `org` is not in the required list because it is absent until the user has an organization; endpoints that need it check it (403 `ORG_REQUIRED`). The `jti` of an access token is unused. **Scope of `leeway=30`:** it applies only to the time claims (`exp`, `iat`, and `nbf` if ever present) inside `jwt.decode`, to tolerate clock skew between containers, so an access token is accepted up to 15 minutes and 30 seconds after issue (clients still see `expires_in` 900). It does not apply to anything evaluated in the database: `refresh_tokens.expires_at`, the 7-day absolute cap and `REFRESH_REUSE_LEEWAY_SECONDS` use `now()` exactly, so a refresh JWT that is inside the 30 s leeway but past `expires_at` is still rejected. The contract (`api-contract.yaml`, Conventions) states the same list.
- **Role is not in the token, and the `org` claim is only a hint.** On each request the backend runs `SELECT role FROM memberships WHERE user_id = :sub AND organization_id = :org`; the tenant context is built from that row, so a role change or removal takes effect immediately. No row (stale or forged-by-bug claim) gives 401, never data.
- **Organization context:** when a user creates an org or accepts an invite the response issues a **new access token** containing `org`; the refresh cookie is **not** rotated for this (the next refresh re-reads the membership). Endpoints that need an org return 403 `ORG_REQUIRED` when `org` is absent (**ASSUMED**: no story or brief text defines this behaviour; the contract marks it ASSUMED). Tenant id is taken only from the verified token plus the membership lookup; no request body, query or path field may set it.
- Failure behaviour: missing/invalid/expired token -> 401 `UNAUTHENTICATED` with `WWW-Authenticate: Bearer` (**ASSUMED**: the brief and stories name only 403 and 404; 401 is the standard reading).
- CORS, security headers, CSP, the `Secure` toggle and log redaction are fixed in ADR-004 (security baseline).
- **Rate limiting** (429 `RATE_LIMITED`, message `Too many requests. Try again later.`, `Retry-After` header with a whole number of seconds, at least 1): approved by the human (brief.md "Human-approved additions", relayed by the Orchestrator on 2026-10-27), for `signup`, `login`, `refresh`, invite `preview` and invite `accept`; **not** for `logout` (stories F1-2 and F3-1 on `main`; F1-2 lists a logout limit, account lockout and limits on other endpoints as out of scope). **The numeric threshold is ASSUMED in the brief and the stories: 10 requests per rolling 60 seconds per client IP per endpoint, counted separately for each endpoint, and a request counts whether or not it succeeds.** Two details are not in the stories and are architect choices: invite `accept` uses the same 10/60 per IP (F3-1 covers only preview), and `POST /organizations` gets a per-user limit of 10/60 (an architect addition from the security review, finding 5, accepted by the Orchestrator).

  | Group | Key | Default (`max/window_seconds`) | Environment variable |
  |---|---|---|---|
  | signup | client IP | 10 / 60 | `RATE_LIMIT_SIGNUP_PER_IP` |
  | login | client IP | 10 / 60 | `RATE_LIMIT_LOGIN_PER_IP` |
  | refresh | client IP | 10 / 60 | `RATE_LIMIT_REFRESH_PER_IP` |
  | invite preview | client IP | 10 / 60 | `RATE_LIMIT_INVITE_PREVIEW_PER_IP` |
  | invite accept | client IP | 10 / 60 | `RATE_LIMIT_INVITE_ACCEPT_PER_IP` |
  | organization create (architect addition) | user id | 10 / 60 | `RATE_LIMIT_ORG_CREATE_PER_USER` |

  - **There is no per-account login limit and no account lockout** (removed in attempt 3: F1-2 puts account lockout out of scope). A per-account limit would help against distributed password guessing but lets an attacker lock a victim out; if security-bot still wants it, it is an extra that needs human approval (listed in the handoff, not in the contract).
  - **Rolling (sliding) window, exact:** every *allowed* request inserts one row into the PostgreSQL table `rate_limit_hits` (data-model.md 3.9); a request is allowed if fewer than `max` rows exist for its bucket within the last `window` seconds. The 429 answer is **not** recorded, so a client that keeps hammering does not extend its own block, and after `Retry-After` seconds a request succeeds (story F1-2 criterion 5). `Retry-After = max(1, ceil(oldest_hit_in_window + window - now))`. The count and the insert run in one transaction under `pg_advisory_xact_lock(hashtext(bucket))`, so concurrent requests cannot both pass at `max - 1`. With at most 10 rows per bucket the count is cheap.
  - **Implementation details (attempt 3):** (1) the limiter is the *first* step of each limited endpoint, before body parsing, the CSRF guard, authentication and Argon2, so invalid and failing requests count too (F1-2: "whether or not they succeed"); (2) time comes only from the database (`clock_timestamp()`), never from worker clocks; (3) the count-and-insert runs in its own short transaction on its own connection (not the request's transaction), so a later rollback does not un-count the hit; (4) the advisory lock key is the 64-bit `hashtextextended(:bucket, 0)`; a hash collision only makes two buckets wait for each other, never mixes their counts, because the count is by the `bucket` text; (5) startup refuses a malformed `RATE_LIMIT_*` value (`<max>/<window_seconds>` with max 1-10000 and window 1-86400); (6) cleanup: on each allowed hit the same transaction deletes that bucket's rows older than the window, and a background task (at startup and every 60 s) runs `DELETE FROM rate_limit_hits WHERE hit_at < now() - interval '1 hour'` so buckets of clients that never return disappear; (7) an attacker who rotates through many IPv6 /64 prefixes creates many buckets but at most `max` rows each for at most an hour, accepted; (8) if no client address can be determined the bucket is `<group>:unknown`. **Tests (qa-bot):** 10 requests pass and the 11th gets 429 with `Retry-After >= 1`; after `Retry-After` seconds the next request passes (F1-2 criterion 5); 20 simultaneous requests, spread over two worker processes, let exactly 10 pass; an invalid body and a wrong password count; the IPv6 /64 grouping; `X-Forwarded-For` from an untrusted peer is ignored; `RATE_LIMIT_ENABLED=false` disables it in test only.
  - **Counter store:** shared by all workers and containers; an in-process limiter is not allowed because it multiplies the limits by the worker count. If the database is unavailable the request fails anyway (503), so the limiter never fails open.
  - **Environment variables so that tests can relax or tighten limits (story F1-2 assumption):** every number is configurable by the variable in the table (format `<max>/<window_seconds>`, default `10/60`), and `RATE_LIMIT_ENABLED` (default `true`) switches all limits off. The **Playwright/e2e compose override sets `RATE_LIMIT_ENABLED=false`** (many signups from one IP), and backend rate-limit tests keep the defaults or set small values. The app refuses to start with `APP_ENV=production` and `RATE_LIMIT_ENABLED=false`. All variables, defaults and owners are in the table in `stack.md`.
  - **Client IP and the reverse proxy (assumption):** exactly one trusted reverse proxy (the nginx container) sits in front of the backend and *overwrites* the header (`proxy_set_header X-Forwarded-For $remote_addr`). `TRUSTED_PROXY_IPS` (comma-separated **exact IP addresses**) lists the peers whose `X-Forwarded-For` may be believed; the backend then uses that single value (if the header holds several comma-separated entries, only the right-most one). **Pinned to the nginx container:** the compose file gives the nginx (frontend) service a fixed address on a dedicated compose network (devops-bot picks the subnet, for example `172.28.0.0/24` with nginx at `172.28.0.10`) and `.env.example` sets `TRUSTED_PROXY_IPS=172.28.0.10`; no subnet, no `*`. The app refuses to start when the value contains `*`, `0.0.0.0/0` or `::/0`, and when it is empty with `APP_ENV=production` (an empty list behind the proxy would put every user in the nginx address's single bucket). uvicorn runs with `--no-proxy-headers` because the application does this parsing itself. For any other peer, `X-Forwarded-For` is ignored and the socket peer address is used, so a client cannot spoof its IP, and no `--forwarded-allow-ips='*'`. If the deployment adds another proxy or load balancer, this setting must be revisited, and the backend port must not be published in a production-like compose file. **IPv6 clients are bucketed by their /64 prefix** (one subscriber usually owns a whole /64), IPv4 by the full address.
  - Because F1-1 requires 409 `EMAIL_TAKEN` on signup, signup stays an email-enumeration oracle that only the per-IP signup limit mitigates (security-bot note 12; a generic signup response would contradict F1-1 and is not done).
- Invite tokens never appear in a server-visible path or query (URL fragment plus POST body); see ADR-003.

## Consequences
- Easier: no external auth service; Argon2id resists GPU cracking; XSS cannot read the refresh token (HttpOnly); a stolen refresh token is detected on reuse and can be revoked, and logout really ends the session on the server; the session is capped at 7 days from login; role changes apply instantly; the token has no tenant-spoofing path.
- Harder / limits:
  - **Refresh tokens are now stateful** (reverses the Attempt 2 decision): the `refresh_tokens` table, one lookup and one transaction per refresh, a cleanup of old rows, and the two-tab race (leeway plus a cross-tab lock in the SPA). Each API request still needs one membership lookup.
  - **Residual risk, not fixed:** XSS can still call `POST /auth/refresh` from the page (the cookie is sent automatically) and obtain access tokens while the page is open; the CSP and text-only rendering in ADR-004 reduce XSS, they do not make it impossible. A 15-minute access token stays valid after logout or revocation.
  - No refresh-token revocation after a password change or reset exists because there is no change/reset flow in the MVP; when one is added it must revoke all families of the user.
- Memory cost: 64 MiB per concurrent hash, capped by `ARGON2_MAX_CONCURRENCY` per worker (hash in a thread pool, `run_in_threadpool`, so the event loop is not blocked).
- Symmetric key: anyone who holds `JWT_SECRET` can mint access tokens (and refresh JWTs, which still need a matching row in `refresh_tokens` to work, so a minted refresh token alone is useless). Keep it out of logs and CI output (CI generates a fresh random value per job, which must pass the same startup check; no real data exists in CI). Rotation without a `kid` logs everyone out.
- Fallback: bcrypt 5.0.0 (cost 12) if argon2-cffi wheels fail to build on a target platform.
